## Design contract

`09-UI-SPEC.md` is binding for this plan: the component inventory, the project's own 4-point
spacing tokens, the two-weight typography rule (300 and 500 only — never 400, 600 or 700), the
accent-reserved-for-four-things colour rule, and the copywriting table are not suggestions.
Read the "Screen Contracts → 1. `/settings/senders`" section before writing any component.

Two rules from it that are easy to lose:
- **Do not add a new symbol to `public/icons.svg`.** Symbols only get Lucide's stroke defaults
  when explicitly added; a freshly added one renders as a solid black blob. Where no suitable
  icon exists, use a text-only control — the existing precedent is the icon-less "Copy link"
  button in `components/dashboard/drill-sheet.tsx`.
- **Use a plain bordered `div`, not `Card`.** `/settings/general` and `/settings/pricing` both
  do; matching them is the point.

**`lib/push/schema.ts`.** Two Zod schemas, the single source of truth for both the client form
and the Server Action. A mint schema taking a sender name: a string, trimmed, minimum 1 and
maximum 100 characters after trimming, with a message that reads like the rest of the project's
validation copy. A revoke schema taking a credential id as a uuid. Infer the TypeScript types
from the schemas rather than declaring them twice.

**`lib/push/credentials.ts`.** Every list-presentation rule as pure functions, so the table
component stays presentational and the rules are unit-testable without a DOM:

  - A credential row type carrying id, sender, token prefix, created-at, last-used-at and
    revoked-at. It deliberately has no field for the token digest — the type itself is the
    reminder that the digest never reaches the browser.
  - A sort taking rows and returning them ordered by sender ascending (compare with `en-GB`
    locale collation, not raw code-unit ordering) then created-at descending. Stable for equal
    keys.
  - A live test: a credential is live when its revoked-at is null.
  - A rotating-senders function returning the set of sender names holding two or more live
    credentials. That set drives the "Rotating" badge (D-02's healthy state, not an alarm).
  - A sole-live test: given all rows and one credential id, is that credential the only live
    one for its sender? It drives the escalation line in the revoke confirmation.
  - A distinct-senders function returning the sender names already present, de-duplicated by
    exact string equality and sorted, for the suggestion chips. **Exact** equality is
    deliberate: "TSYS" and "tsys" are two entries, because they really are two identities in a
    table with no unique constraint on sender — surfacing both is what lets the operator notice
    the typo and pick the right one, which is precisely why the chip row exists.
  - A last-used formatter returning the `en-GB` medium-date short-time string when the
    timestamp is present, and null when it is not, so the component renders the "Never used
    yet" treatment rather than the formatter inventing copy.

**`app/(dashboard)/settings/senders/actions.ts`.** Two Server Actions, cloning
`app/(dashboard)/settings/general/actions.ts` object-for-object:

  - `issuePushCredential`: `safeParse` the input against the mint schema and return the
    flattened error on failure. Build the **session-scoped** client from
    `@/lib/supabase/server` — never the secret-key client — and return an unauthorized result
    if there is no user. That choice is load-bearing, not stylistic: the audit trigger reads
    `auth.uid()`, which is null under the secret key, and an audit row with no actor defeats
    D-03. Call `generateToken()`, insert the sender, the digest, the prefix and the acting user
    as creator, and return a success result carrying the **complete token**, the prefix and the
    sender. That return value is the only place the complete token ever exists outside the
    generating function; say so in the doc comment, and do not log it, do not put it in the
    error path, and do not write it anywhere else (D-05). On a database error, log the raw
    error server-side only and return a friendly message, exactly as the existing actions do.
    `revalidatePath("/settings/senders")`.
  - `revokePushCredential`: `safeParse` against the revoke schema, same session client and user
    guard, then update the row's revoked-at to now where the id matches **and** revoked-at is
    still null. Ask for the affected rows back and treat zero rows as a friendly "this
    credential is already revoked" result rather than a silent success — a revoke that quietly
    did nothing is the kind of lie this whole milestone exists to eliminate.
    `revalidatePath("/settings/senders")`.
  - Neither action ever selects or returns the token digest.

**`components/settings/token-reveal-dialog.tsx`** (client component). The show-once surface. A
toast is wrong here and a dialog is right, because a toast auto-dismisses and this is a secret
that can never be re-shown. Binding behaviours:

  - A warning banner using the warning tokens — never the destructive ones — because this is a
    caution about an irreversible-but-successful action, not a failure. Heading "Copy this token

    truncated, beside a "Copy token" button using the same clipboard call as
    `drill-sheet.tsx`. A resolved write raises the toast "Token copied". A **rejected** write —
    which happens in an insecure context or when permission is denied — raises a destructive
    toast reading "Copy failed — select the token and copy manually" and leaves the dialog
    open. Handle the rejection explicitly; an unhandled rejection here silently loses a
    show-once secret.
  - The only control that closes the dialog is a button reading "I've saved it — done". The
    phrasing is the acknowledgment, which is why it is not a bare "Close" or an icon. Closing it
    fires the success toast "Credential issued for {sender}." and refreshes the list.
  - The complete token lives only in this component's props for the life of the dialog. It is
    never written to a ref that outlives the dialog, never to the URL, never to storage, and
    never logged.

## Flagged planner assumptions

**AUTO-04 was returned `unclassified` by the edge probe.** No edge predicate was derived for it
and the planner has not invented one. Two concrete questions are therefore carried forward as
assumptions rather than silently resolved:

1. **Revocation versus a request already in flight.** The assumption is that a push whose
   credential lookup already succeeded completes, because the lookup happens once at the top of
   the request and is not re-checked per file. The window is milliseconds and the failure mode
   is one extra file accepted from a just-revoked token, which drain will still ingest normally.
   If that window matters to the business, it needs a decision, not a code change smuggled in
   here.
2. **Sender-name equality under case and Unicode normalisation.** `push_credentials.sender` has
   no unique constraint (D-02) and no normalisation, so "TSYS", "tsys" and a form that differs
   only by Unicode normalisation are three distinct identities the database will accept. The
   mitigation is presentational — the suggestion chip row shows exactly what already exists so
   the operator picks rather than retypes — not structural. Whether sender names should be
   normalised or case-folded at write time is an open product question.

**Both are surfaced for the developer, not resolved by this plan.**
