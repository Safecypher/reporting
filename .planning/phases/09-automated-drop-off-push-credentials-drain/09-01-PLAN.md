<objective>
Prove the whole Phase 9 delivery spine end-to-end on one thin path: a sender with a live
credential pushes a file, the bytes land in a private `inbox` bucket under a
server-generated key, the drain trigger picks that object up, runs it through the
**unchanged** `ingest()`, and the resulting `ingested_files` row carries the provenance that
traces back to the push response.

Purpose: every later plan in this phase expands one layer of this slice (delivery rejections,
the credential admin page, the uploads-history surfacing, the live schedule). If the spine is
wrong, they all are — so it is built and proved first, on the executor's best context.

Output: one migration, the delivery and drain cores behind injectable seams, both route
handlers, the `proxy.ts` matcher exclusion without which neither route is reachable, and an
automated test that drives push → inbox → drain → ingest over fakes.

**Migration `supabase/migrations/0040_push_delivery_spine.sql`.** Follow
`0023_app_settings.sql`'s comment density and object order. It creates, in one file:

  - The private `inbox` Storage bucket, inserted into `storage.buckets` with public false,
    idempotent on conflict. No client RLS policies at all — it is reached only by the
    secret-key server client, the same access model the `reports` bucket uses in
    `0004_rls_and_storage.sql`.
  - `push_credentials`: uuid id default gen_random_uuid(); `sender` text not null **with no
    unique constraint** (D-02, confirmed in Task 1 — carry a comment saying so explicitly and
    naming the rotation reason, because the design doc's own line says otherwise and a future
    reader will otherwise "fix" it); `token_sha256` text not null unique; `token_prefix` text
    not null (D-04 — the non-secret display prefix, stored as its own column at mint time);
    `created_at`, `created_by` referencing auth.users, `last_used_at` nullable, `revoked_at`
    nullable.
  - Three additive columns on `ingested_files`, declared **after** `push_credentials` exists:
    a text `source`, not null, defaulting to 'manual', constrained to 'manual', 'push' or
    'email'; a nullable text `source_ref`; and a nullable `source_credential_id` uuid
    referencing `push_credentials(id)`. The default is what makes every existing row correct
    with no backfill (AUTO-06). Keep 'email' in the constraint now even though nothing writes
    it — CONTEXT.md's deferred email-bridge adapter is then a no-migration change. The FK
    column exists because D-15 requires the uploads history to show the **sender name**, which
    means resolving a file back to the credential that accepted it; a real foreign key makes
    that an embedded PostgREST join in plan 09-04 instead of a lossy string-prefix match
    against the sanitised object key.
  - RLS on `push_credentials`: enable it, then add an authenticated **select**, authenticated
    **insert** and authenticated **update** policy, and deliberately no delete policy — the
    same L-04 "audit, not restriction" shape `app_settings` uses in `0023`. This is a
    deliberate divergence from the design doc's "no client policies at all": CONTEXT.md D-01
    requires `/settings/senders` to write through the **session-scoped** client so `auth.uid()`
    reaches the audit trigger, and a policy-free table makes that impossible. Say so in the
    comment. Then close the gap the policies open by revoking **column-level select** on
    `token_sha256` from anon and authenticated, so the digest is reachable only by the
    secret-key client that performs the push lookup; insert privilege on that column stays, so
    the mint action can write it without ever being able to read it back.
  - `push_credentials_audit` mirroring `app_settings_audit` object-for-object (D-03):
    identity bigint pk, `changed_by` uuid referencing auth.users, `changed_at`, the action
    ('issued' or 'revoked'), the sender, the token prefix, and a `summary` text. The audit row
    carries the prefix and NEVER the token or its hash — state that in the table comment.
    Populate it from a SECURITY DEFINER trigger `fn_push_credentials_audit()` with
    `set search_path = public`, firing after insert and after update, stamping `auth.uid()`.
    Revoke execute on that function from public, anon and authenticated, exactly as
    `0023` does for `fn_app_settings_audit()`. RLS on, authenticated select only — no client
    insert, update or delete policy, so the trail cannot be forged or erased.
  - `drain_lock`: the row-mutex that replaces the design doc's literal `pg_try_advisory_lock`.
    09-RESEARCH.md Pattern 2 is the reason — a session-scoped advisory lock taken in one
    request and released in another does not survive Supabase's transaction-mode pooling, so
    the release can silently no-op against a different pooled backend. A singleton row
    (`id smallint primary key default 1 check (id = 1)`, `running boolean not null default
    false`, `started_at timestamptz`) seeded once on conflict do nothing. This is the concrete
    resolution of CONTEXT.md's "the advisory-lock key for the drain route" discretion point —
    record that in the file comment.
  - `fn_try_acquire_drain_lock()` returning boolean, language sql, SECURITY DEFINER,
    `set search_path = public`: a single UPDATE of the singleton row setting running true and
    started_at now, whose WHERE clause admits the caller when running is false **or** when
    started_at is older than ten minutes, returning true. A stale-lock reclaim window is
    required, not optional: without it, one route crash before the release blocks every future
    drain forever, which is a self-inflicted denial of service on a job that runs once a day.
  - `fn_release_drain_lock()` returning void, same language/security/search_path, setting
    running false and started_at null unconditionally — idempotent, so a release with no
    matching acquire is a no-op rather than an error.
  - Revoke execute on both functions from public, anon and authenticated.

**`lib/ingestion/supabase-writer.ts` — additive only.** Two changes, no behaviour change for
existing callers:

  - Widen `createSupabaseWriter` to take an optional second parameter carrying an optional
    provenance source ('manual' | 'push' | 'email'), an optional provenance reference string
    and an optional credential id. Hold all three in the same per-call closure that already
    holds `currentFileId`. In `recordFile`, build the insert payload as a named local object
    that adds the three provenance fields — source defaulting to 'manual', reference and
    credential id defaulting to null — and pass that variable to `.insert(...)`. Passing a
    *variable* rather than an object literal is deliberate: TypeScript's excess-property check
    applies to fresh literals only, so the three columns that `types/db.ts` does not yet know
    about type-check without a cast and without an eslint suppression. Do not touch the
    storage-upload call, the retry loop, or any other method. This is 09-RESEARCH.md Pitfall
    1's seam: the provenance rides in the **writer factory's closure**, never in `ingest()`'s
    `meta` argument, which is why `lib/ingestion/index.ts` and `lib/ingestion/types.ts` stay
    untouched.
  - Add `export` to the existing `buildSecretClient`, `sanitiseFileName`, `detectContentType`
    and `isXlsx`. No body changes — one implementation of the path-injection defence and one of
    magic-byte format detection, now reachable from `lib/push/*`.

**`lib/push/tokens.ts`.** A prefix constant of `sc_live_`; `generateToken()` returning the
complete token (prefix plus 32 random bytes base64url — 256 bits of entropy), the stored
display prefix (the constant plus the first 8 characters of the random part, per D-04's
worked example), and the hex SHA-256 digest; and `hashToken(token)` returning that same hex
digest. `node:crypto` only — `randomBytes` and `createHash`, never a hand-rolled generator.
The complete token is returned to exactly one caller and is never logged (D-05).

**`lib/push/tables.ts`.** One exported helper taking a Supabase client and a table name and
returning the query builder for a table `types/db.ts` does not yet describe, with a single
documented eslint suppression, mirroring the escape hatch `upsertRows` already carries. Every
`push_credentials` / `drain_lock` query in this plan goes through it, so the untyped surface is
one auditable file rather than four. Name in its doc comment that 09-05's type regeneration is
what retires it.

**`lib/push/delivery.ts` — `acceptPush`.** Pure over injected dependencies, so it is testable
without a network or a database: a credential lookup by token digest, a last-used stamp, and an
object put. It takes the request's authorization header value, the declared content length, and
the ordered list of files, and returns an HTTP status plus a positional per-file result array.
Behaviour on this path:

  - Refuse before buffering when the declared content length exceeds 25MB (D-09) — the same
    pre-buffer discipline `app/api/ingest/route.ts` already applies at 5MB. Exactly at the cap
    is accepted; only strictly greater is refused.
  - Read the bearer token from the authorization header. Hash it, then look up the credential
    where the digest matches and the revocation timestamp is null (D-10). This is a lookup,
    not a comparison — there is no secret-dependent branch to time, and an unknown token and a
    revoked token are answered identically, so senders cannot be enumerated. No token, a
    malformed header, an unknown token and a revoked token all answer 401.
  - The sender comes from the returned credential row and from nowhere else (D-10). There is no
    URL segment, form field or header that can name a sender.
  - Stamp the credential's last-used timestamp after a successful lookup.
  - For each file, in the order the parts arrived: refuse a file strictly larger than 5MB;
    otherwise build the object key as the **credential id**, a slash, then an ISO-8601 basic
    timestamp, a positional index, a short random suffix and the sanitised filename. The
    credential id as the leading segment is what lets the drain hand a real foreign key to the
    writer, which is what makes D-15's sender-name column an exact join rather than a
    string-prefix guess — and it sidesteps the "TSYS" versus "tsys" key-prefix ambiguity that
    D-02's deliberately non-unique sender column allows. The positional index plus the random
    suffix is what makes two same-named files in one request two distinct objects rather than a
    collision, and the put uses upsert false so a key clash surfaces as an error rather than
    silently overwriting a sender's earlier file. Sanitise the filename with the writer's
    `sanitiseFileName`. Derive the object's content type from the bytes with the writer's
    `detectContentType`, never from the client's declared type.
  - Return one result entry per input file, in input order, each carrying the filename, an
    accepted flag and — when accepted — the object key as the `reference` (D-08). That string
    is the one the sender quotes at 7am and the one `source_ref` will hold.
  - Zero files in the request answers 400 with an empty result array; all files accepted
    answers 202 (D-07). The 207 and per-file rejection branches are plan 09-02's expansion —
    leave the status selection expressed as "every file accepted → 202, otherwise 400" so
    09-02 inserts 207 without reshaping the function.

**`lib/push/drain.ts` — `drainInbox`.** Pure over injected dependencies: acquire mutex, release
mutex, list a prefix, list the bucket root, download an object, remove an object, and an
ingest-one callback. Behaviour:

  - Try to acquire the mutex first. If it is held, return a skipped outcome carrying HTTP 409
    and do nothing else — no listing, no download, no ingest.
  - List the bucket root to find credential-id prefixes. Storage returns folder pseudo-entries
    whose metadata is null; treat those as prefixes to descend into and real entries as
    objects. Sort prefixes ascending and objects within a prefix ascending, so processing order
    is a stated rule rather than listing luck.
  - Per object: download the bytes, convert the returned Blob to a Uint8Array, and call the
    ingest-one callback with the object key and bytes. Remove the object from the inbox once
    that callback returns a terminal outcome — including a failed one, per the design doc's
    D-9: the original bytes are already persisted to `reports` by `recordFile` and the outcome
    is already in `ingested_files`, so nothing is lost. An **unexpected throw** deliberately

**`app/api/ingest/drain/route.ts`.** Same nodejs runtime. Read the drain secret from the
process environment; if it is absent, answer 500 and do no work — fail closed, never open.

and comparing the digests with `node:crypto`'s `timingSafeEqual` (equal-length inputs are
guaranteed by hashing first). A mismatch answers 401. The cron secret and a sender token are
different things and are never interchangeable. Then call `drainInbox` with dependencies bound
to the two lock functions via `.rpc(...)`, to `supabase.storage.from("inbox")`, and to an
ingest-one callback that constructs a **fresh** `createSupabaseWriter(client, { source: 'push',
sourceRef: objectKey, sourceCredentialId: <the key's leading segment when it parses as a uuid,

name, its bytes, an undefined content type and a null uploader. One writer per file is
mandatory, not stylistic: the writer's own doc comment states its per-call closure state, and
reusing one across a batch cross-wires file ids and provenance (09-RESEARCH.md Pitfall 4).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| TSYS / Bit Addict → `POST /api/push` | Fully untrusted internet traffic carrying a bearer token, a declared Content-Length and attacker-shaped filenames and bytes. No session, no CSRF context. |
| `pg_cron` (Postgres) → `POST /api/ingest/drain` | A public HTTPS endpoint reachable by anyone; only the shared cron secret distinguishes the real caller. |
| Route handler → Supabase secret-key client | The secret key bypasses RLS entirely; every query on this side of the boundary is unconstrained by policy. |
| Inbox object bytes → `ingest()` | Sender-controlled file content entering the parsing pipeline. |
