<objective>
Make the uploads history answer the question people actually ask of it: *who sent this, and what
happened to it?* A pushed file names its sender; a refused file appears in the same list rather
than a second place; and the object reference that ties a sender's "we sent it at 06:04" to a
dashboard figure is one click away.

Purpose: this is where AUTO-06's provenance becomes visible, and where the milestone's thesis —
nothing silently missing — is tested. A morning where every delivery was refused must not render
as an empty, reassuring table.

Output: a pure merge module, the two reads behind it, and the extended table.
</objective>

from it that are easy to lose:

  <action>
A new module owning the merge and every derived string, so the table stays presentational and
the rules are testable without a DOM — the same split `lib/upload/batch.ts` already uses for the
dropzone.

Define a combined row type that both a real upload and a delivery rejection can inhabit: a
discriminating kind, an id, a timestamp, a filename, a source label, a status, optional accepted,
duplicate and rejected counts, an optional rejection reason, and an optional source reference.
Rejection rows carry no counts and no source reference by construction — nothing was parsed and
nothing was ever written to Storage, because the structural checks refused the file first.

`mergeHistory` takes the ingested-file rows and the rejection rows and returns one list ordered
by timestamp descending. When two rows share a timestamp the order is decided by a **stated**
secondary key — kind first (uploads before rejections) then id ascending — so the list is
deterministic and stable rather than dependent on which query resolved first. Say so in a
comment; "sorted by time" alone is not a specification when timestamps collide.

`sourceLabel` derives the Source column's text per D-15, from the sender name rather than the
mechanism: a pushed file reads the joined sender name; a rejection reads its own denormalised
sender; a manual upload reads "Manual — " followed by the uploader's email, falling back to
"Manual — unknown user" when the identity cannot be resolved. Never a raw UUID: no
email-resolving view exists in this codebase — the same gap `/settings/pricing`'s audit log
already documents and accepts — and a UUID in this column would read as a bug rather than a
known gap to the three people who use this table.

`formatCount` renders a present count as its number and an absent one as an em dash. This is a
correctness rule, not styling: a rejection row has no counts at all, and rendering zero for all
three would claim the file was processed and found empty, which is a different and false
statement from "this file was never parsed".

Export the two status labels as constants — the existing parse-failure label and the new
delivery-refusal label — so the deliberate distinction between them lives in one place rather
than as two string literals in a component.

`lib/upload/__tests__/history.test.ts` covers: interleaving of three uploads and two rejections
into one correctly ordered list; the tie-break when an upload and a rejection share a timestamp,
asserted to be stable across a reversed input order; an empty-uploads-with-rejections case
returning a non-empty list (the case the table's empty state must not swallow); both-empty
returning an empty list; each of the three source-label branches including the unknown-user
fallback; and `formatCount` returning an em dash for null and undefined and the number for zero.
That last case matters — a genuine zero-row upload renders 0, while an absent count renders the
dash; the two are not the same thing.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `push_rejections.file_name` / `.reason` → rendered table cell | Text originating from a sender-supplied filename, crossing into the operator's browser. |
| `ingested_files.source_ref` → clipboard | A server-generated string, but one the operator will paste elsewhere. |
| Session-scoped read → RLS | The page reads both tables as the logged-in user; policy, not application code, decides what is visible. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-24 | Tampering | sender-supplied filename rendered in a table cell | medium | mitigate | Rendered as React text content, never as HTML and never through a dangerous-HTML escape hatch; React escapes it. The filename was already sanitised before becoming a Storage key, but the displayed value is the original and is treated as untrusted text. |
| T-09-25 | Information Disclosure | uploader identity | low | accept | The uploader UUID is deliberately never rendered; the fallback copy is shown instead. No email-resolving view exists, which is a recorded, accepted gap rather than something this plan invents a workaround for. |
| T-09-26 | Information Disclosure | `push_rejections` readable by any authenticated user | low | accept | Consistent with the project's existing no-RBAC posture — every authenticated user already sees the full uploads history. |
| T-09-27 | Repudiation | a refused delivery that never appears on screen | high | mitigate | The empty state is gated on the combined list length, and rejection rows interleave inline; the merge is unit-tested for the zero-uploads-with-rejections case specifically. |
| T-09-SC | Tampering | npm/pip/cargo installs | high | accept | No new package is installed — every primitive is already in `components/ui/`. |
</threat_model>
