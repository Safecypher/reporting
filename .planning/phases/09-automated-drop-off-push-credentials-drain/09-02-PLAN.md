<objective>
Turn the tracer's happy-path delivery into the contract Safecypher will actually publish to two
external senders: cheap structural checks at the door, a durable record for every refusal, and
the 202 / 207 / 400 status matrix with a per-file result array.

Purpose: D-07 is a costly-to-change published contract. Getting the shape right — and covered
by tests — before it is handed to TSYS and Bit Addict is the entire point of doing it in its
own plan rather than bolting it onto the tracer.

Output: the `push_rejections` table, `acceptPush`'s validation and rejection machinery, and the
route wiring that gives an external sender an honest, per-file answer.
</objective>

## Scope fences

- `lib/ingestion/` is untouched. `ingest()` is not called from this plan at all — delivery and
  interpretation stay separate, which is the whole of design-doc D-5.
- `classify()`, `extractHeaderSignature` and every parser stay out of `/api/push` (D-12).
- No hash lookup happens in the delivery path (D-13). A re-pushed file is accepted.
- The drain route and `lib/push/drain.ts` are not modified by this plan.

  <context>
    CONTEXT.md D-14 answers: a new table. The forcing fact is that
    `ingested_files.content_sha256` is unique and **every zero-byte file has the same SHA-256**,
    so a sender posting an empty file on two consecutive mornings would collide on the second.

    The two alternatives were both rejected for concrete reasons: relaxing the unique constraint
    to a partial index weakens the guarantee the entire de-duplication story rests on, for the
    sake of rows that are not really files; and upserting so the newest rejection overwrites the
    last destroys exactly the "this sender has failed every morning this week" signal the
    rejection record exists to provide.

    This is rated one-way: once rejections and real files live in separate tables, merging them
    later is a migration plus a rewrite of every reader, not a refactor.

**Migration `supabase/migrations/0041_push_rejections.sql`.** One table, commented in the house
style of `0023_app_settings.sql`, carrying an explicit note about why it is separate from
`ingested_files`:

  - Columns: uuid `id` primary key default gen_random_uuid(); `credential_id` uuid referencing
    `push_credentials(id)`, nullable so a rejection that happened before the credential lookup
    succeeded can still be recorded; `sender` text not null, denormalised at write time so the
    uploads history can render it without a join (D-16); `file_name` text not null; `reason`
    text not null; `byte_size` bigint nullable; `rejected_at` timestamptz not null default
    now().
  - **No unique constraint of any kind beyond the primary key**, and a comment saying why: a
    unique key over sender, filename and reason would collide on exactly the repeat-failure
    case this table exists to make visible — the same trap, one table over, that D-14 was
    written to avoid in `ingested_files` (09-RESEARCH.md Pitfall 5). Do not add one "for
    hygiene".
  - An index on `rejected_at` descending, since the only read is the uploads history's
    reverse-chronological list.
  - RLS enabled with an authenticated **select** policy and no insert, update or delete policy:
    rows are written exclusively by the secret-key client inside the push route, and the
    uploads history reads them through the session-scoped client. Mirror
    `app_settings_audit`'s policy shape.

**`lib/push/delivery.ts` — the structural checks.** Extend `acceptPush`, keeping its dependency
interface and positional result array from 09-01 and adding a rejection-recording dependency.
Per D-11 these are **cheap structural checks only** — nothing that parses:

  - Zero length. A file part with no bytes is refused. This is first because it is the case
    that drove D-14 into existence.
  - Per-file size: strictly greater than 5MB is refused; exactly 5MB is accepted.
  - Format by magic bytes: accept only a file whose bytes begin with the ZIP magic number (an
    XLSX container) or whose bytes are plausibly text (i.e. not the ZIP magic, since five of
    the six reports are CSV). Reuse the writer's exported `isXlsx`; do not re-implement the
    test and do not look at the filename extension or the client's declared content type. Add
    one genuinely new check here that `isXlsx` does not cover: a byte array containing a NUL
    byte in its leading kilobyte is neither CSV nor XLSX and is refused as an unrecognised
    binary format. Keep the check to that — anything more is parsing, which belongs at drain.

  Each refusal produces (a) a result entry carrying the filename, a not-accepted flag and a
  short, fixed reason string, and (b) exactly one `push_rejections` row via the injected
  recorder. The reason strings are a closed set defined as exported constants in this module so
  the route, the tests and plan 09-04's uploads-history rendering all read the same text: an
  empty-file reason, an over-size reason, and an unrecognised-format reason. They are curated
  copy in the manner of `lib/upload/batch.ts` — never a database error, never a stack trace,
  never a path from this server.

  A request-level refusal (declared content length over 25MB, missing or invalid credential)
  answers before any file is read and records nothing in `push_rejections`: there is no sender
  identity to attribute a row to in the unauthenticated case, and the over-size case has no
  per-file breakdown to record. Say so in a comment so the omission reads as a decision rather
  than an oversight.

  Then the status matrix, exactly D-07: every file accepted answers 202; at least one accepted
  and at least one refused answers 207 Multi-Status; none accepted — including the zero-file-
  parts case — answers 400. Every one of the three carries the full per-file result array.
  Note in the module doc comment that 207 was chosen knowing it is an unusual code for a
  third-party integrator, because the per-file honesty was judged worth it and it mirrors the
  dropzone's existing continue-on-failure batch behaviour.

  There is still no hash lookup anywhere in this path (D-13). A file the sender pushed
  yesterday is accepted today and reported `alreadyUploaded` at drain.

**`lib/push/__tests__/delivery.test.ts`.** The published contract under test:

  - Status matrix: three files all good answers 202; two good and one empty answers 207; one
    file that is empty answers 400; zero file parts answers 400.
  - Positional ordering with a rejection in the middle: three parts where the second is
    oversized returns three entries, the second not accepted, and the first and third still
    carrying their references.
  - Reasons: each of the three reason constants is produced by its own case, and each case
    writes exactly one `push_rejections` row carrying the sender, the filename and that reason.
  - Boundaries: a one-byte file is accepted; a file of exactly 5,242,880 bytes is accepted; a
    file of 5,242,881 bytes is refused.
  - Magic bytes: a file named with a spreadsheet extension whose bytes are plain text is
    accepted and typed as CSV; a file named with a CSV extension whose bytes start with the ZIP
    magic number is accepted and typed as XLSX; a file whose leading bytes contain a NUL is
    refused as unrecognised.
  - Duplicate acceptance: pushing byte-identical content twice yields two accepted results with
    two distinct references and zero rejection rows.
  - Isolation: the rejection recorder is never called on the unauthenticated path or the
    request-too-large path.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Sender-supplied file bytes → structural checks | Arbitrary bytes, arbitrary count, arbitrary declared sizes, all attacker-controlled. |
| Rejection reason → external sender | Text crossing back out to a third party; anything internal in it leaks. |
| Rejection row → `push_rejections` | A write path an unauthenticated caller must not be able to reach or flood. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-12 | Information Disclosure | rejection reason text | medium | mitigate | Reasons are a closed set of exported constants; no database error, stack trace or server path is ever placed in a reason, following `lib/upload/batch.ts`'s existing curated-copy rule. |
| T-09-13 | Denial of Service | `push_rejections` flooding | medium | mitigate | Rows are written only after a successful credential lookup, so an unauthenticated caller cannot write any; the request-level refusals record nothing at all. |
| T-09-14 | Tampering | client-declared Content-Type or extension steering format | medium | mitigate | Format is decided by the file's own leading bytes via the writer's `isXlsx` (D-11); neither the extension nor the declared type is read. |
| T-09-15 | Denial of Service | many small file parts in one request | medium | accept | The 25MB request cap bounds total work; per-part count is not separately capped because a sender's whole morning batch is six files and a count cap would refuse a legitimate future batch. Revisit if a real sender ever sends hundreds of parts. |
| T-09-16 | Repudiation | a refusal with no record | high | mitigate | Every per-file refusal writes a `push_rejections` row before the response is assembled; a failed insert is logged server-side rather than swallowed. |
| T-09-SC | Tampering | npm/pip/cargo installs | high | accept | No new package is installed by this plan. |
</threat_model>
