<objective>
Give this codebase the id→email resolution capability it has never had, and use it to
close G-09-1: the /uploads Source column attributing a manual upload to the signed-in
user who performed it, as locked decision D-15 specifies (`Manual — <uploader email>`).

Purpose: D-15 was implemented for pushed files and rejections but not for manual
uploads, because no mechanism existed to turn `ingested_files.uploaded_by` (a uuid)
into a display identity. `mergeHistory()` therefore passed a null uploader
unconditionally at lib/upload/history.ts:95, making `sourceLabel()`'s email branch
unreachable in production. The identity was captured correctly upstream
(app/api/ingest/route.ts:59) and read correctly by the page
(app/(dashboard)/uploads/page.tsx:27) — it was discarded at the merge. The fix is
therefore half schema (the missing capability) and half wiring (the discarded value).

Output: migration 0045 creating a two-column `profiles` table synced from
`auth.users` by trigger and backfilled; a shared `lib/identity/profiles.ts` resolver;
`mergeHistory` taking the resolved identities; the uploads page supplying them; and a
record of the live catalog readings that prove the grants and RLS actually took.
</objective>

Statements, in this order (the order is load-bearing and must be stated as such in
the file's comments):

1. `create table if not exists profiles` with exactly three columns: `id uuid primary
   key references auth.users(id) on delete cascade`, `email text`, and `updated_at
   timestamptz not null default now()`. `email` is deliberately NULLABLE — Supabase
   permits an auth user with no email (phone-only), and a not-null constraint here
   would make the sync trigger able to break a sign-up. The resolver treats a null
   email as unresolved, which is the honest reading. Per the UAT-close constraint,
   this table mirrors ONLY id and email from `auth.users`; no other auth column is
   copied, and no view over `auth.users` is created.

2. `create or replace function fn_sync_profile_from_auth_user()` returning `trigger`,
   `security definer`, `set search_path = public`, `language plpgsql`. Body: a single
   `insert into profiles (id, email, updated_at) values (new.id, new.email, now()) on
   conflict (id) do update set email = excluded.email, updated_at = now();` then
   `return new;`. It must read only `new.id` and `new.email` and must never select
   from `auth.users` — that containment is what stops a SECURITY DEFINER function on
   a protected schema from becoming a general auth-schema reader (T-09-14/T-09-15).
   Follow 0040's `fn_push_credentials_audit` for the security-definer shape.

3. `create trigger trg_sync_profile_from_auth_user after insert or update of email on
   auth.users for each row execute function fn_sync_profile_from_auth_user();`. Drop
   it first with `drop trigger if exists ... on auth.users;` so the migration is
   re-runnable.

4. Backfill, AFTER the trigger exists so there is no window where a concurrent write
   is missed: `insert into profiles (id, email) select id, email from auth.users on
   conflict (id) do update set email = excluded.email, updated_at = now();`. Without
   this every historical `ingested_files.uploaded_by`, `pricing_tier_audit.changed_by`,
   `app_settings_audit.changed_by` and `push_credentials_audit.changed_by` would stay
   unattributed — a going-forward-only table does not close this gap.

5. `alter table profiles enable row level security;` then one policy,
   `"profiles_select_authenticated"`, `for select to authenticated using (true)`.
   Deliberately no insert/update/delete policy: the SECURITY DEFINER trigger is the
   sole writer and runs as owner, exactly as 0040 reasons about
   `push_credentials_audit`.

6. `revoke all on profiles from anon, authenticated;` then `grant select (id, email)
   on profiles to authenticated;`. BOTH statements are required and the order is the
   whole point — state this in the comment, citing 0042 and 0044 by filename. Revoke
   first because Supabase grants table-wide privileges on every `public` table by
   default and a narrower column grant cannot carve a hole out of a live table-level
   grant. Revoke ALL rather than just SELECT because TRUNCATE is not row-level and RLS
   does not govern it. `anon` is granted nothing at all.

7. `revoke execute on function fn_sync_profile_from_auth_user() from public, anon,
   authenticated;` — matching 0040/0023/0029. The trigger still fires regardless of
   grants, since a trigger runs as the function owner.

8. `comment on table profiles` and `comment on column profiles.email` recording: what
   the table is for (resolving an actor uuid to a display identity for
   `ingested_files.uploaded_by` and the three `*_audit.changed_by` columns), that it
   holds exactly two mirrored columns and nothing else from `auth.users`, that the
   trigger is the sole writer, and that the revoke-then-column-grant pair must not be
   "simplified" back to a column-level revoke.

Add nothing else. In particular do NOT add a foreign key from `ingested_files` or any
audit table to `profiles`: the resolver reads profiles as a separate keyed lookup, so
no PostgREST embed relationship is needed and no new constraint can fail on apply.
