<objective>
Stop the three change-history surfaces rendering a raw `auth.users` uuid as the person
who made a change, now that plan 09-06 has given this codebase the id→email
capability that was missing.

Purpose: G-09-1's `chosen_approach` states the scope explicitly — "Scope includes
fixing /settings/pricing's raw-UUID actor at the same time, since it is the same
missing capability." `/settings/pricing:132` is the named surface. `/settings/general`
and `/settings/senders` carry the byte-identical mapping and the identical defect;
Task 2 closes them because fixing one of three would leave two pages disagreeing with
the one that was fixed, which reads as a bug rather than a known gap.

This plan is presentation only. No migration, no schema read beyond the `profiles`
select 09-06 already built, no change to any audit trigger — attribution is still
stamped by the SECURITY DEFINER triggers from `auth.uid()`, exactly as before. All
that changes is what the uuid is rendered as.

Output: three Server Components each resolving their audit actors through the one
shared rule.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser session → the three settings pages | All three sit behind the `proxy.ts` auth gate; only an authenticated internal user reaches them. This plan changes what such a user is shown, not who can reach it. |
| `profiles` read → rendered actor label | The one new data flow: a uuid read from an audit table is used as a key into a server-side map, and the value is rendered. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-18 | Information Disclosure | colleague email addresses rendered in three change-history lists | low | accept | The audience is the same authenticated three-person internal team, and email is not secret within this tool (stated at UAT close). This is a net reduction in disclosure, not an increase: the surface previously rendered an `auth.users` primary key to the identical audience, which is the more sensitive of the two values. |
| T-09-19 | Spoofing | the rendered actor identity | medium | mitigate | No client-supplied value reaches the label. The id comes from `*_audit.changed_by`, stamped by a SECURITY DEFINER trigger from `auth.uid()`; the email comes from `profiles`, whose only writer is 0045's owner-run trigger. `actorLabel` resolves through a server-built map and can only return a mapped email or the shared unresolved constant. |
| T-09-20 | Repudiation | an actor that cannot be resolved | low | mitigate | `actorLabel` never falls back to the raw id and never guesses. An unresolvable actor renders the unresolved label, which is a truthful statement rather than a silent omission — the row itself is still displayed with its summary and timestamp intact. |
| T-09-21 | Denial of Service | a failed `profiles` read blanking a settings page | medium | mitigate | The resolver's error is deliberately kept out of each page's combined `ErrorState` branch. A lost email degrades one column; it must not cost an operator the pricing form or the FY settings. Asserted by Task 1's and Task 2's `<done>` and by the human-check on /settings/general. |
| T-09-SC | Tampering | npm/pip/cargo installs | n/a | accept | No packages are installed and no dependency is added; `package.json` is asserted untouched in `<verification>`. |
