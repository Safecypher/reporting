<objective>
Close **WR-02** and **WR-03** — the two robustness findings the verifier explicitly asked be
*tracked rather than dropped* — and then walk the whole phase through a browser, which no session
has yet done.

**WR-02:** with 0033's trigger live, the Server Action must stop writing
`tsys_live_cards_baseline_as_of`. Leaving the write in place would mean two layers competing for
one column, and the action's value would be the one the trigger then has to override on every
save — a rule that works only by accident.

**WR-03:** `fetchAlignmentSettings` currently catches every query error and returns
`DEFAULT_ALIGNMENT_SETTINGS` (`baselineOffset: 0, toleranceCount: 0`), logging server-side only.
Every alignment badge on the page for that request is then computed from assumed values with
nothing on screen saying so. A tolerance read failure and an admin deliberately choosing zero
tolerance are different situations that currently render identically — the same "confidently
wrong because the underlying data wasn't actually there" problem the phase is built to catch
everywhere else, one level down.

Purpose: D-09's guarantee is that a stale offset is *a visible, correctable fact*. Both findings
attack that guarantee from opposite ends — one makes a stale offset look fresh, the other makes an
unread setting look chosen.

Output: the action's narrowed write payload, a discriminated settings result, a scoped notice
component wired into three surfaces, and a completed human walkthrough.
</objective>
