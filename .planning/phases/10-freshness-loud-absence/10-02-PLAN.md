<objective>
Settle D-15 before any UI is built on top of it: can a `postgres`-owned SECURITY DEFINER
function actually reschedule the `daily-drop-off` pg_cron job on this project?

Purpose: Phase 9's largest surprise was a planned mechanism that turned out not merely hard
but unreachable (`pg_has_role('postgres','supabase_auth_admin','MEMBER')` is false), which
killed a migration mid-execution and cost a checkpoint. The orchestrator's live addendum to
10-RESEARCH.md says every precondition for `cron.alter_job` reads true this time — but
privilege to call a function is not the same as a successful call. This plan spends one cheap
measurement to make plan 10-05 a build rather than a gamble.

Output: a measured verdict and `lib/settings/drain-schedule.ts` carrying it as a git-tracked
constant with the evidence in its doc comment.
</objective>

  <name>Task 1: Run the four-query reachability probe against the live project</name>

  <precondition>The orchestrator holds live Supabase access to this project — a working
  Supabase MCP connection, or `SUPABASE_ACCESS_TOKEN` set with an authenticated
  `supabase` CLI. Executors in this project hold neither (09-LEARNINGS, "Checkpoint the work
  an executor structurally cannot do"), so this task is performed by the orchestrator, never
  dispatched to a subagent.</precondition>

  <action>
    Run the D-15 reachability probe against the live project — four read-only catalog queries
    plus one transaction-wrapped dry run of `cron.alter_job` — and report the verdict with the
    actual returned rows. An executor cannot do this: it has no Supabase MCP tool and the
    local `supabase` CLI returned 401 Unauthorized during research, which is why this is a
    checkpoint the orchestrator performs rather than a task any subagent can be handed.
  </action>

  <instructions>
    Run these in order and paste the ACTUAL returned rows into the plan summary — not "as
    expected". Verifying against the live catalog rather than against the SQL you just ran is
    the discipline `0040`'s silent-no-op revoke established.

    1. Confirm the job's stored owner, addressed BY NAME:
       `select jobid, jobname, username, schedule, active from cron.job where jobname = 'daily-drop-off';`
       Expected from the orchestrator addendum: jobid 2, username `postgres`, schedule
       `0 16 * * *`, active true. Record the jobid you observe but do NOT hardcode it
       anywhere — pg_cron's access control keys on `username`, and the id is
       environment-specific.

    2. Confirm the calling identity and whether it bypasses RLS at all:
       `select current_user, session_user, rolsuper, rolbypassrls from pg_roles where rolname = current_user;`

    3. Confirm EXECUTE is genuinely reachable, not merely present by default:
       `select has_function_privilege(current_user, 'cron.alter_job(bigint,text,text,text,text,boolean)', 'EXECUTE') as can_alter, has_function_privilege(current_user, 'cron.unschedule(bigint)', 'EXECUTE') as can_unschedule;`

    4. The real test, wrapped so nothing sticks. This MUST be submitted as ONE whole-body
       statement, never statement-by-statement — a harness that commits each statement
       separately would leave the production schedule altered:
       `begin; select cron.alter_job((select jobid from cron.job where jobname = 'daily-drop-off'), schedule := '1 16 * * *'); select jobid, schedule from cron.job where jobname = 'daily-drop-off'; rollback;`
       PASS is the inner read returning `1 16 * * *`. There are TWO distinct failure shapes
       and both must be checked: a raised error (a `42501`-family permission denial), and a
       silent no-op where the statement succeeds but the read-back still shows
       `0 16 * * *` — `cron.alter_job` returns void and pg_cron's RLS filters rather than
       raising, so an unchanged read-back is a real failure even with no error.

    5. Re-read the schedule AFTER the rollback and confirm it is `0 16 * * *` again:
       `select jobname, schedule from cron.job where jobname = 'daily-drop-off';`

    Report the verdict as exactly one of: REACHABLE (step 4's read-back showed the probed
    value and step 5 confirmed the rollback), UNREACHABLE-ERROR (step 4 raised, quote the
    SQLSTATE and message verbatim), or UNREACHABLE-NOOP (step 4 succeeded but the read-back
    was unchanged).

    This is the "checkpoint the work an executor structurally cannot do" pattern established
    by 06-09, 09-05 and 09-06. It carries `gate="blocking-human"` because the whole point of
    D-15 is that a human sees the measured answer before plan 10-05 builds an operator-facing
    control on top of it; auto-approving an assumed PASS would reproduce exactly the Phase 9
    failure this task exists to prevent.
  </instructions>

  <verification>
    Re-read `select jobname, schedule, active from cron.job where jobname = 'daily-drop-off';`
    and confirm it reads `0 16 * * *` and active — the probe must leave the production
    schedule exactly as it found it. The reported verdict must be one of the three defined
    strings, and the summary must carry the ACTUAL returned rows from all five steps rather
    than a paraphrase.
  </verification>

  <resume-signal>Report REACHABLE, UNREACHABLE-ERROR, or UNREACHABLE-NOOP, with the actual rows from steps 1-5 pasted in.</resume-signal>
</task>
