<objective>
Make the daily freshness check's run time something Richard or Andy can move, and prove the
`cron.alter_job` mechanism plan 10-02 measured actually works through the app's normal
request path.

Purpose: D-14. Reading the roadmap literally, SC-5 only asked for the thresholds. D-14 goes
further, because a job scheduled before the day's last delivery reports a false absence every
morning, and an alarm that cries wolf daily is an alarm nobody reads — so the time it runs is
exactly as operationally load-bearing as the thresholds it evaluates.

and the SECURITY DEFINER `cron.alter_job` wrapper), the run-time form, and the section wired

    **A. The column.** `alter table app_settings add column drain_cron_run_time time not null
    default '16:00'` with a check constraint pinning it to whole minutes is unnecessary —
    `time` already carries what is needed — but DO add
    `check (drain_cron_run_time = date_trunc('minute', drain_cron_run_time))`, because
    `cron.alter_job` takes a five-field cron expression that cannot express seconds, and a
    stored value with a seconds component would be silently truncated on its way to the job.
    A comment must state that the default `'16:00'` is deliberately equal to the schedule
    `0043` set live, so applying this migration cannot move a job nobody meant to move, and
    that `0043`'s comment block remains the record of WHY 16:00 was chosen and why it is
    labelled PROVISIONAL. Times are UTC — the cron job runs in the database's own zone.

    **B. The audit widening, forward-only.**
    `alter table app_settings_audit add column old_drain_cron_run_time time, add column
    new_drain_cron_run_time time;` then `create or replace function fn_app_settings_audit()`
    reproducing the CURRENT body from `0035` verbatim and adding exactly one more
    `summary_parts` branch — fired only when `old.drain_cron_run_time is distinct from
    new.drain_cron_run_time` — reading `'Daily check run time changed to ' ||
    to_char(new.drain_cron_run_time, 'HH24:MI') || ' UTC'`, plus the two new columns in the
    insert's column list and values. Do not alter any existing branch, the `auth.uid()` stamp,
    the empty-array fallback, or the `array_to_string(summary_parts, '; ')` join: an FY-only
    edit must still produce byte-identical summary text. Re-run
    `revoke execute on function fn_app_settings_audit() from public, anon, authenticated;`
    after the `create or replace` — a replaced function gets fresh default grants.

    **C. The wrapper.** `create function fn_set_drain_cron_schedule(p_run_time time) returns
    void, language plpgsql, security definer, set search_path = public, cron`. Body:
    - Build the cron expression from the argument, never from client-supplied text:
      `v_schedule := extract(minute from p_run_time)::int || ' ' || extract(hour from p_run_time)::int || ' * * *'`.
      Taking a `time` rather than a `text` schedule is the point — there is no way for a caller
      to inject a different cron expression, a different job, or extra fields.
    - Look the job up BY NAME at call time:
      `select jobid into v_jobid from cron.job where jobname = 'daily-drop-off';` and
      `raise exception 'daily-drop-off cron job not found'` when it is null. Never hardcode a
      jobid — pg_cron keys access control on `cron.job.username` and the id is
      environment-specific (the orchestrator addendum observed jobid 2 on this project and
      explicitly says not to rely on it).
    - `perform cron.alter_job(v_jobid, schedule := v_schedule);` — `alter_job`, not
      unschedule-then-reschedule, so the job mutates in place and cannot transiently vanish if
      a second statement fails.
    - Then READ BACK and verify: re-select `schedule` for that jobid and
      `raise exception 'cron.alter_job did not take effect: schedule is still %', <observed>`
      when it does not equal `v_schedule`. This is not belt-and-braces. `cron.alter_job`
      returns void and pg_cron's RLS filters rather than raising, so the silent no-op is a real
      failure shape on this platform — and this project has already shipped one grant statement
      that reported success while doing nothing (`0042`). Raising here is what lets the Server
      Action roll its own `app_settings` write back instead of leaving the page asserting a
      schedule that is not in force.
    - Grants:
      `revoke execute on function fn_set_drain_cron_schedule(time) from public;` then the same
      `from anon;` then `grant execute on function fn_set_drain_cron_schedule(time) to authenticated;`.
      A function that can reschedule a production job must never be reachable by `anon`.
      A comment must state that this is deliberately callable by `authenticated` under L-04 —
      this codebase has no RBAC, and D-13's answer to that is audit, not restriction — and that
      the audit for a run-time change is the `app_settings_audit` row the trigger writes.

    Add nothing else. This migration must not create a second cron job: `0043` states EXACTLY
    ONE JOB, and the reason is D-4's ordering hazard — a freshness check that fires before its
    drain reports "never arrived" for a file still sitting in the inbox.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `saveDrainRunTime` Server Action | A directly-invocable endpoint whose downstream effect is rescheduling a production job. |
| PostgREST → `fn_set_drain_cron_schedule` | A SECURITY DEFINER function in the public schema is a callable RPC unless EXECUTE is narrowed. It can change when the ingestion job runs. |
| `app_settings` row → `cron.job` | Two stores that must agree. Divergence is silent by default. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-19 | Elevation of Privilege | `fn_set_drain_cron_schedule` | high | mitigate | SECURITY DEFINER with `set search_path = public, cron`; `revoke execute … from public;` and `… from anon;` before `grant execute … to authenticated;` (the `0014`/`0023`/`0027` precedent). Deliberately callable by `authenticated` under L-04 — no RBAC exists in this codebase and D-13's answer is audit, not restriction — with the `app_settings_audit` row as the attribution. |
| T-10-20 | Tampering | cron-expression injection | high | mitigate | The wrapper takes a `time`, not a `text` schedule, and composes the five-field expression itself from `extract(minute …)` and `extract(hour …)`. There is no caller-controlled path to a different job, a different expression, or extra cron fields. |
| T-10-21 | Denial of Service | mis-targeting or losing the job | high | mitigate | The job is looked up by `jobname = 'daily-drop-off'` at call time and the function raises when it is absent; `cron.alter_job` mutates in place so the job never transiently vanishes; no `cron.schedule` or `cron.unschedule` call exists, so no second daily job can be created against `0043`'s EXACTLY ONE JOB rule. |
| T-10-22 | Repudiation | a silent no-op reschedule | high | mitigate | The wrapper reads `cron.job.schedule` back after the alter and raises when it is unchanged. `cron.alter_job` returns void and pg_cron's RLS filters rather than raising, so a silent no-op is a real failure shape here — and this project has already shipped one grant that reported success while doing nothing (`0042`). The raise is what makes the Server Action's compensating write reachable. |
| T-10-23 | Tampering | stored setting diverging from the live schedule | high | mitigate | The Server Action restores the previous `drain_cron_run_time` when the RPC errors, so the two stores cannot be left disagreeing; the compensating write produces its own audit row, recording that someone tried to move the run time and it did not take. When `DRAIN_SCHEDULE_EDITABLE` is false the action refuses before touching the database, so the Server Action is not a back door around a mechanism the deploy declared unavailable. |
| T-10-SC | Tampering | npm/pip/cargo installs | high | mitigate | package-legitimacy gate + blocking human checkpoint for [ASSUMED]/[SUS]. This plan installs no package — it uses `Input`, `Label` and `Button`, all already present in `components/ui/`. |
