<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → app | All browser code may only hold the publishable key; the secret key must never cross this boundary |
| unauthenticated request → dashboard/API routes | proxy.ts is the first gate; untrusted requests must be redirected before any data route runs |
| npm registry → build | Third-party packages execute at install/build time |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Elevation of Privilege | proxy.ts route gate | mitigate | Matcher covers all non-login paths; `getUser()` (server-verified, not a stale cookie) gates redirect; RLS added in Plan 03 as an independent second layer |
| T-01-02 | Information Disclosure | Supabase key handling | mitigate | Only `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in browser/proxy clients; `SUPABASE_SECRET_KEY` never imported into client/proxy code (verified by acceptance criteria) |
| T-01-03 | Spoofing | Session cookie refresh | mitigate | Use `@supabase/ssr` getAll/setAll only; call getUser() before response is committed (Pitfall 3) so refreshed cookies persist; no custom token logic |
| T-01-SC | Tampering | npm installs (scaffold + shadcn) | mitigate | RESEARCH Package Legitimacy Audit: all 10 Phase 1 packages slopcheck `[OK]`, no postinstall scripts; pinned exact versions; no `[ASSUMED]`/`[SUS]` packages so no blocking legitimacy checkpoint required |
</threat_model>
