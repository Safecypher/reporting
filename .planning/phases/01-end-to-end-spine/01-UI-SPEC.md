# Phase 1 — UI Design Contract

> Visual and interaction contract for the End-to-End Spine phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope:** login screen (AUTH-01/02/03), authenticated app shell + auth boundary, drag-and-drop upload surface with per-upload result feedback (INGEST-01/02/04), and the verifications-over-time dashboard view (DASH-01/04).
>
> **Standing contract:** This is a greenfield project with no existing brand or code. The tokens defined here are the design foundation for **all** later phases (revenue, SLA, reconciliation). Every choice below is a decision made in the absence of a CONTEXT.md (discuss-phase was not run) and is recorded with rationale so it can be reviewed or overridden.

---

## Design Aesthetic (Decision)

**Decision:** Clean, professional, neutral internal-tool aesthetic — a dense, trustworthy financial reporting surface, not a marketing site. Light theme first. Prioritise data density, legibility, aligned numerics, and calm neutrals so that colour is available to carry *meaning* (authenticated vs failed, OK vs discrepancy) rather than decoration.

**Rationale:** PROJECT.md describes an internal reconciliation tool for a small technical team where the core value is *trustworthy* revenue reconciliation. Trust is served by restraint: neutral chrome, one accent, semantic colour reserved for data state. Density (14px body, compact tables) suits a data-heavy operator dashboard.

## Visual Hierarchy & Focal Points

Each screen has one declared primary visual anchor so the executor does not have to guess where the eye should land.

| Screen | Primary anchor (focal point) | Secondary anchors | Tertiary / chrome |
|--------|------------------------------|-------------------|-------------------|
| Login | The sign-in `card` centred in the viewport, with the `Sign in` primary button as the action focus | Heading `Sign in to Safecypher Reporting` | Muted helper text, background |
| Upload surface | The drag-and-drop zone (largest interactive surface, dashed border, centred prompt) | Post-upload result summary card (accepted / duplicates / rejected) | Uploads history table below |
| **Verifications-over-time dashboard** | **The time-series chart** (authenticated vs failed over time) — it is the largest element, top of content, and the reason the screen exists (DASH-01) | The KPI **Display (28px)** metric cards (e.g. total verifications, % authenticated) sit as a secondary row that summarises the chart | The `Daily/Weekly/Monthly` toggle, the `Data as of last import` badge, and the data-window caption are supporting controls/meta, not focal points |

**Verifications dashboard layout intent:** chart occupies the dominant upper region as the single focal point; the 28px KPI Display values form a secondary summarising band (glanceable numbers that the chart explains); the granularity toggle sits adjacent to the chart title; freshness badge and data-window caption are quiet meta near the header. Colour emphasis (accent blue / amber series) lives in the chart — the surrounding chrome stays neutral so the data reads first.

## Spacing Scale

Declared values (8-point scale, all multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, inline chip padding |
| sm | 8px | Compact element spacing, badge padding |
| md | 16px | Default element spacing, card inner padding |
| lg | 24px | Section padding, gap between cards |
| xl | 32px | Layout gaps, page content padding |
| 2xl | 48px | Major section breaks, empty-state vertical rhythm |
| 3xl | 64px | Page-level top spacing / hero-less page header offset |

**Exceptions:** Dense data tables use **12px** vertical cell padding (a multiple of 4) instead of 16px to raise row density — appropriate for an operator reconciliation tool. Minimum interactive control height 32px (shadcn `sm`) / 36px default; this is a desktop internal tool, so 44px touch targets are **not** required.

## Typography

Deliberately dense: 14px body (not the 16px consumer default), 4 sizes, 2 weights.

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Display | 28px | 600 (semibold) | 1.2 | KPI / metric values on summary cards (e.g. total verifications, % authenticated) |
| Heading | 20px | 600 (semibold) | 1.2 | Page title, section / card titles |
| Body | 14px | 400 (regular) | 1.5 | Default UI text, table cell values, form fields, descriptions |
| Label | 12px | 600 (semibold) | 1.4 | Table column headers, field labels, badges, "as of" meta, captions |

**Weights:** exactly two — regular (400) and semibold (600). No light, medium, or bold.
**Decision — 14px body:** density over the 16px default; standard for financial/operator dashboards. Recorded so it can be overridden if reviewers prefer 16px.

## Color

Light theme, expressed as shadcn CSS variables (slate base). 60/30/10 split:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F8FAFC` (slate-50) | App background / main content surface |
| Secondary (30%) | `#FFFFFF` (white) + `#F1F5F9` (slate-100) | Cards, sidebar/nav, table headers, panels |
| Accent (10%) | `#2563EB` (blue-600) | See reserved-for list below |
| Destructive | `#DC2626` (red-600) | Error/rejection state and confirmations only |

Base text: `#0F172A` (slate-900) primary, `#64748B` (slate-500) muted/secondary. Borders: `#E2E8F0` (slate-200).

**Accent (blue) reserved for:** primary buttons (`Sign in`, `Upload report`), the active navigation item, focus rings, text links, and the primary/"Authenticated" chart series. **Never** used for: card borders, body text, generic icons, table chrome, or as a decorative fill.

### Data-Visualisation Palette (load-bearing for this and all later phases)

Charts carry meaning through colour, so the semantic palette is part of the contract. Chosen to be **colour-blind-safe** (blue/amber pairing, not red/green):

| Semantic role | Value | Used for |
|---------------|-------|----------|
| Positive / Authenticated / OK | `#2563EB` (blue-600) | "Authenticated" verification series; OK reconciliation state (later phases) |
| Negative / Failed / Attention | `#D97706` (amber-600) | "Failed" verification series; needs-review state (later phases) |
| Discrepancy / Breach / Error | `#DC2626` (red-600) | SLA breaches, confirmed mismatches, rejected-row counts (later phases) |
| Neutral / Reference | `#64748B` (slate-500) | Reference lines (e.g. the 750ms SLA line in Phase 3), gridlines, secondary series |

Chart rules: label axes; show a legend for multi-series; tooltips show exact integer counts with tabular numerals; never rely on colour alone — pair failed/breach series with a distinct label and (where space allows) a shape/pattern or icon in the legend.

## Copywriting Contract

Plain, precise, operator-facing language. No marketing tone. Numbers are always explicit (accepted / skipped / rejected) — silent failure is forbidden per INGEST-04 and PITFALLS Pitfall-UX.

| Element | Copy |
|---------|------|
| Primary CTA (upload) | `Upload report` |
| Primary CTA (login) | `Sign in` |
| Login screen heading | `Sign in to Safecypher Reporting` |
| Login helper | `Internal team access only.` |
| Upload zone (idle) | `Drag a report file here, or click to browse` with sub-label `CSV or XLSX` |
| Upload zone (dragging) | `Drop to upload` |
| Upload zone (uploading) | `Uploading and processing…` |
| Upload success summary | `Import complete — {accepted} rows accepted · {duplicates} duplicates skipped · {rejected} rejected` |
| Upload rejected-rows detail | `{n} rows rejected:` followed by a per-reason list (e.g. `12 — missing timestamp`, `3 — invalid date`) |
| Empty state heading (verifications view, no data) | `No verifications yet` |
| Empty state body (verifications view) | `Upload the daily verification report to see authenticated vs failed volume over time.` + inline link `Upload report` |
| Empty state (uploads history) | `No uploads yet. Drag a report file above to get started.` |
| Error state (unrecognised file) | `Unrecognised file. This doesn't match any known report type — check you're uploading the daily verification report (CSV or XLSX).` |
| Error state (upload failed / server) | `Upload failed. The file couldn't be processed — try again, and if it keeps happening, check the file isn't corrupted.` |
| Duplicate-file notice | `This file appears to have already been uploaded on {date}. Re-uploading won't change any totals.` |
| "As of" freshness meta (DASH-04) | `Data as of last import: {timestamp}` |
| Data-window caption | `Excludes data before 13 Aug 2026.` |
| Granularity toggle options | `Daily` · `Weekly` · `Monthly` |
| Series legend labels | `Authenticated` · `Failed` |
| Sign-out control | `Sign out` |

**Destructive actions in this phase:** **None.** Ingested records are immutable (PROJECT.md / DATA-07); corrections are made by re-uploading a corrected file (idempotent de-dup), never by editing or deleting rows. `Sign out` is non-destructive and needs no confirmation. If any destructive control is added later, it requires an AlertDialog confirmation naming the exact action.

## Interaction & State Contract (trust-critical)

Every data surface MUST implement four states — missing any one breaks the "no silent failure / know how current the data is" contract:

1. **Loading** — `skeleton` placeholders (chart + cards), never a blank flash.
2. **Empty** — the empty-state copy above with a clear next action (upload).
3. **Populated** — data with the `Data as of last import: {timestamp}` freshness badge (DASH-04) and the data-window caption always visible.
4. **Error** — the error copy above; the failure is shown, never swallowed.

Upload-specific contract (INGEST-04): after every upload the user sees the accepted / duplicates-skipped / rejected breakdown, with per-reason detail for rejects. Unrecognised files are rejected with the explicit message above (INGEST-02). Focus rings (accent blue) are visible on all interactive elements for keyboard users.
