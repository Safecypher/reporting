<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous user → dashboard routes | Must be blocked at both proxy.ts (Plan 01) and the layout guard (this plan) |
| login form → Supabase Auth | Credentials cross to Supabase; no custom password storage or comparison |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Spoofing | Credential handling | mitigate | Supabase Auth handles password hashing/verification; app never stores or compares passwords; no signup surface (D-01) reduces attack surface |
| T-02-02 | Elevation of Privilege | Layout guard | mitigate | Server-Component `getUser()` redirect is a second, independent enforcement layer behind proxy.ts (defence-in-depth per Security Domain V4) |
| T-02-03 | Information Disclosure | Login error copy | accept | Generic invalid-credentials message avoids leaking whether an email exists; low risk for a 4-user internal tool |
| T-02-04 | Repudiation | Sign-in events | accept | Supabase Auth logs auth events; per-action audit beyond ingestion is out of scope for Phase 1 |
</threat_model>
