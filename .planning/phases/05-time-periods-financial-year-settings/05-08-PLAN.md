<objective>
Close UAT gap **G-05-OBS1**: below 768px the navigation cannot be opened at all.

The root cause is already established and is NOT to be re-derived: `app/(dashboard)/layout.tsx`
renders shadcn `<Sidebar>`, which below the `MOBILE_BREAKPOINT` of 768px (`hooks/use-mobile.ts`)
renders as a `Sheet` whose open state starts false, and no `<SidebarTrigger>` is rendered anywhere
in the application — grep-confirmed, the only occurrence is its own definition in
`components/ui/sidebar.tsx`. The nav is therefore not merely hidden on mobile; there is no control
that can reveal it.

This defect originates in the Phase 1 app shell, not Phase 5. It was found during Phase 5 UAT
test 1 (the 375px scope-badge check) and the user chose to close it here.

Purpose: an internal reporting tool that leadership opens on a phone must at minimum let them
reach a second page. Every period-scoped view shipped in this phase is unreachable on mobile
today, which makes PERIOD-01's "every metric view" claim untrue for anyone on a small screen.

Output: a small-viewport-only top bar carrying the sidebar trigger, wired into the authenticated
shell.

**Explicitly out of scope (must not regress):** the desktop sidebar layout at 768px and wider, the
server-side `getUser()` session guard, the nav item list itself, and every metric view. This plan
touches two files in the app shell and nothing else.
</objective>

    - hooks/use-mobile.ts — the 768px breakpoint the Tailwind `md` utilities must agree with
    - app/(dashboard)/layout.tsx — the whole file; note the inner `main` nested inside SidebarInset's own `main`
  </read_first>
  <action>
Create `components/app-shell/mobile-nav-bar.tsx` exporting a `MobileNavBar` component. It is a plain composition with no client state of its own, so it needs no client directive — `SidebarTrigger` is already a client component and works as a child of the server layout because `SidebarProvider` sits above it in the tree.

Render a `header` element that is hidden from the `md` breakpoint upward, sticks to the top of the scroll container, sits above page content in stacking order, and carries the same bottom hairline and background treatment the shell already uses — the `border-b border-border` plus `bg-background` pairing used by the existing page headers. Inside it, lay out a `SidebarTrigger` followed by the Safecypher mark, using the same `next/image` logo source, alt text and dimensions the existing `SidebarHeader` uses, scaled to sit on a compact bar. Give the trigger an explicit accessible name of `Open navigation` via `aria-label`; the component's built-in screen-reader span is generic and an `aria-label` takes precedence over it.

Tailwind's `md` breakpoint is 768px, which is exactly the `MOBILE_BREAKPOINT` the sidebar's own `useIsMobile` hook uses — state the correspondence in a comment on the hidden-from-md utility so a future breakpoint change to one is not made without the other, since a mismatch would either show a dead trigger on desktop or leave a gap where neither the sidebar nor the bar renders.

Wire it into `app/(dashboard)/layout.tsx` as the first child of `SidebarInset`, before the page content. `SidebarInset` already renders a `main` element, so replace the inner `main` wrapper with a `div` carrying the identical `flex flex-1 flex-col` classes: this keeps the rendered layout byte-identical while collapsing the pre-existing main-inside-main nesting, and it avoids the alternative of nesting a `header` inside a nested `main`. Change nothing else in the layout — the `getUser()` redirect guard, the `SidebarProvider`, the `Sidebar` and all of its children stay exactly as they are.
