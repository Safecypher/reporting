<objective>
Close UAT gap **G-05-5**: the tier editor silently minted a new tier set that superseded the
signed TSYS MSA ladder for all revenue from that date onward, with no confirmation and nothing on
screen distinguishing "creating a new set" from "editing the selected one".

The root cause is already established and is NOT to be re-derived: `components/pricing/pricing-tier-form.tsx:212`
exempts a brand-new tier set from the restate dialog by design (pattern P-04 from 05-04-PLAN.md).
That exemption is correct for the genuinely-first tier set and wrong for a new set that lands on
top of an active one. This plan splits those two cases apart.

**One design correction the executor must not "simplify" away.** The gap text says a new set must
warn when it "would supersede an active set from a date already carrying revenue activity". Taken
literally as an activity-day count, the warning would still NOT have fired in the live incident:
the stray set was effective 2026-09-10 while ingested data ran only to 2026-09-08, so the elapsed
activity-day count was zero. The trigger implemented here is therefore the **structural** fact —
an existing tier set already prices the proposed effective date — and the activity-day count is
carried into the dialog copy as extra detail, not used as the gate. This is strictly stronger than
the literal reading and never weaker (D-17, D-18).

Purpose: a change to live contract pricing must never happen without the operator seeing what it
replaces. This is the "trustworthy revenue reconciliation" core value applied to the pricing input
itself — a silently superseded MSA ladder mis-prices every downstream revenue and reconciliation
figure while every screen still reads green.

Output: a pure, tested supersede resolver; a create-supersede confirmation dialog; an always-on
create-vs-edit mode statement plus an inline pre-submit notice; and a warning-toned, actionable
effective_from collision message.

**Explicitly out of scope (must not regress):** the existing edit-path restate dialog and its day
count (D-18/P-04), the data-window coverage guard on save and delete (D-19, migration 0025), the
delete confirmation flow, and the D-06 per-month tier-summation invariant. This plan adds a gate
and re-tones one message; it removes no guard.
</objective>
