# Phase 5 — UI Design Contract

> Visual and interaction contract for Time Periods & Financial-Year Settings. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope:** a period-lens control cluster + active-scope indicator added to all five metric
> views (`/`, `/verifications`, `/revenue`, `/sla`, `/cards`, `/reconciliation`); a new
> `/settings/general` page for the FY-start setting; and the pricing admin's edit-in-place +
> generalized-delete + restate-warning surfaces (D-17/D-18/D-19) on `/settings/pricing`. The
> TSYS tier seed itself (D-14) is a migration/data concern with no new UI beyond what's already
> specified for the pricing editor.

> **Standing contract:** This phase does **not** invent a new visual language. It is a **strict
> extension** of `.planning/phases/01-end-to-end-spine/01-UI-SPEC.md` (brand tokens, shadcn→brand
> mapping, 4-state contract, copy voice), `.planning/phases/03-revenue-sla-drill-down/03-UI-SPEC.md`
> (money formatting, pricing-form conventions, drill-down Sheet), and
> `.planning/phases/04-reconciliation-discrepancy-flagging/04-UI-SPEC.md` (`StatusBadge`, dense
> tables). Only what is new to Phase 5 — the period lens, the active-scope indicator, the
> period-empty state, `/settings/general`, and the pricing editor's edit-in-place/restate-warning
> surfaces — is specified below. Where this document is silent, defer to 01 → 03 → 04, in that
> order.

## Design Aesthetic (Decision)

**Decision:** Unchanged — clean, professional, trustworthy internal-tool aesthetic, Cypher Blue
as the single lead, 1pt hairlines over shadows, pill buttons, calm neutrals so colour carries
meaning. Phase 5 introduces one new "meaning" domain: **temporal scope**. The period lens must
read as a **first-class, always-visible fact about the page** — not a buried filter — because
success criterion 2 requires every view to state which scope produced its numbers. The design
answer is to promote the scope statement to the same header row that already carries the
`Data as of last import` freshness badge (01-UI-SPEC.md DASH-04), rather than inventing a new
chrome region.

**Rationale:** D-03's default-period change (all-time → current month) means the exact same page
can now show materially different numbers depending on an invisible URL param. For a revenue-
reconciliation tool, an ambiguous scope is as dangerous as a wrong number — the scope indicator is
therefore treated with the same "no silent failure" rigor as freshness and error states.

**Destructive actions in this phase:**
1. **Delete a pricing tier set** (generalized from "latest only" to "any set", D-19) — `Dialog`
   confirmation naming the exact effective date, unchanged mechanism from Phase 3, copy updated
   above.
2. **Save an in-place tier-set edit that restates history** (D-17/D-18) — not a deletion, but
   treated with the same two-step-confirmation rigor because it silently changes a past revenue
   figure if the user clicks through without reading. Uses `--warning` styling (not
   `--destructive`) per the Color section's binding rule. A same-set edit that does **not** touch
   any already-elapsed day (e.g. correcting a future-dated set before it takes effect) skips the
   dialog entirely and saves immediately — the warning is reserved for edits that actually restate
   history, never shown reflexively on every save.
3. **FY-start change** (D-13) — audited but **not** dialog-gated; an inline notice is sufficient
   (see Interaction contract for the reasoning).

## Interaction & State Contract (trust-critical)

Every period-scoped data surface keeps the **same 4-state contract as Phase 1/3/4** — period
scoping adds a **fifth, explicitly-not-a-state-machine-state** value:

1. **Loading** — unchanged, existing skeletons.
2. **Empty (no data at all)** — unchanged, existing per-view empty state (e.g. "No verifications
   yet") — used only when the *entire* data source has nothing, regardless of period.
3. **Populated** — unchanged, plus the new active-scope badge is always present alongside
   `FreshnessBadge` whenever the view is populated.
4. **Error** — unchanged, existing per-view error state.
5. **Period-empty (new, not a 5th state-machine state — a value the "populated" branch can take)**
   — data exists somewhere in the source, but the *selected* period has none. Rendered with its
   own copy/icon (see Copywriting), calm and neutral (never `--warning`/`--destructive`), with a
   `View current month` recovery action. **Binding distinction:** period-empty must never reuse the
   domain empty-state's "Upload report" CTA — uploading won't fix an already-correct absence of
   data for a past period, so that CTA would be actively misleading.

**Scope indicator binding rule (success criterion 2):** the active-scope badge always reflects the
period **actually applied** to the query, not the raw URL param — if a param was invalid and fell
back to the D-03 default, the badge shows the fallback, never the invalid input. This keeps the
badge trustworthy under the same "no silent failure" principle as the freshness badge.

**Historical navigation contract (D-07):**
- Month/year `select` options are reverse-chronological (most recent first) and hard-capped at the
  current UTC month/year — the control never offers a future period, since D-06's correctness
  invariant means a future period can only ever be empty and offering it just adds a dead-end.
- The data-window floor (13 Aug 2026) is not separately enforced in the picker UI — the earliest
  month/year option is naturally 13 Aug 2026's month/year, since no data exists before it.
- Selecting any option updates the URL immediately (no "Apply" button), matching the existing
  Granularity/Timezone toggle's instant-feedback convention (D-01/D-02 mean this is a real
  navigation, not a client-side re-slice, but the *feel* — click, see new numbers — must be
  identical to the user).

**FY/CY toggle visibility (D-08, binding):** rendered only when Period = Year; unmounted (not
just visually hidden) for Month and All-time, so it never holds stale selection state that could
apply invisibly.

**`/settings/general` contract:**
- The scope-impact notice is **always visible** near the field pair (not conditionally shown), so
  a user understands the blast radius before they even start editing — contrast with the
  restate-warning `Dialog` on `/settings/pricing`, which appears only when a save would actually
  restate something.
- On successful save, the change appears immediately at the top of the audit log (same
  optimistic/refetch choice as `/settings/pricing`, D-13).

**`/settings/pricing` contract (extensions):**
- Selecting an existing set in the new `Tier set` selector populates the form (`effectiveFrom`,
  `resetWindow`, `tiers`) with that set's current values for in-place editing (D-17) — the
  `effectiveFrom` field, previously constrained to "strictly after the latest existing" (Phase 3),
  is now freely editable, including backdating.
- Submitting a form that would change a rate or boundary applying to a day on or before "today"
  (UTC) intercepts with the restate-warning `Dialog`; a purely-future edit saves immediately with
  no dialog.
- The delete action generalizes to whichever set is currently selected in the `Tier set` selector,
  not implicitly "the latest" — the confirmation `Dialog` always names the exact effective date
  being removed.
- A delete attempt the server rejects (would leave no set covering 13 Aug 2026, per the
  code_context guard) surfaces as a toast error using the "Generalized delete blocked" copy above
  — never a silent no-op.

Focus rings (brand `--focus-ring`) visible on all new interactive elements (`select` trigger,
period/FY `ToggleGroup`s, tier-set selector) — unchanged rule from Phase 1/3/4.
