<objective>
Close code-review BLOCKER **CR-01** / UAT gap **G-05-CR01**: moving an existing tier set's
`effective_from` across another tier set's date silently transfers pricing authority for the days
between them, with nothing on screen naming the set being displaced.

The root cause is already established and independently confirmed — **do not re-derive it.**
`lib/pricing/restate-scope.ts:63-71` (`resolveEditImpact`) hardcodes `supersedes: null`, and its
doc comment at lines 66-68 asserts an edit "never displaces a different one". That is true at the
ROW level and false at the PRICING level. `v_revenue_tier_set_by_day`
(`supabase/migrations/0012_v_revenue.sql`) resolves each day's tier set with
`where effective_from <= day order by effective_from desc limit 1` — authority is decided purely
by RELATIVE `effective_from` ordering, with no notion of "this row already covered that day".
Migration 0025's UPDATE path guards only the data-window floor, not reordering. 05-07 closed the
CREATE half of this defect class and deliberately scoped the EDIT half out. This plan closes the
other half.

Purpose: this is the same defect class that produced a real live incident during UAT — a save
that silently superseded the signed TSYS MSA ladder while every screen still read green. "We
manage our own destiny" (PROJECT.md core value) means a change to live contract pricing must
never happen without the operator seeing what it replaces. A mis-priced day propagates into every
revenue and reconciliation figure downstream.

Output: a corrected pure resolver with an honest doc comment; a third confirmation variant naming
the displaced set; an inline pre-submit notice that now covers edit mode; a replacement of the
test that pins the wrong invariant; and a date guard whose name matches its behaviour.

**A trap this plan must handle head-on.** `lib/pricing/__tests__/restate-scope.test.ts:143` is
titled as a universal claim that an edit can never produce a supersede. Note carefully: that test
will **still pass** after the fix (its fixture's other set is dated 2026-01-01, earlier than the
edited set's own 2026-08-13, so nothing is displaced) — so an executor could leave it in place and
break nothing today. It must be deleted anyway. Its TITLE enshrines a universal that is now false,
and a future reader "restoring the invariant" would reintroduce exactly this blocker. Task 1
replaces it with two case-specific tests. The justification for deleting a passing test is stated
here and must be restated in the SUMMARY.

**Explicitly out of scope (must not regress, and must not be "improved" in passing):**
the 05-07 create-path supersede gate and every one of its committed cases; the D-19 data-window
coverage guard and its copy/tone on both save and delete; the D-06 per-month tier-summation
invariant (no revenue view, no marginal-bracket RPC, no migration is touched by this plan); the
`getUser()` guard on every Server Action; WR-01 (no raw Postgres text to the client). Also
deliberately untouched: `lib/dashboard/drill-params.ts:53`, which carries the same weak
`Date.parse` date check as the guard fixed here — it is a separate open review item on URL param
parsing for the drill views, and widening this plan into it risks a regression in a subsystem this
gap does not concern.

**No new migration.** The fix lives entirely in application code. Migrations 0023-0026 are already
pushed live; nothing here needs a 0027.
</objective>
