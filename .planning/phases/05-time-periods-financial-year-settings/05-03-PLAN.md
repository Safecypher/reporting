<objective>
Make the financial-year start a real, editable, audited setting. Build `/settings/general` as a
strict clone of `/settings/pricing`'s proven shape — Zod schema shared by client and server, a
react-hook-form editor, a Server Action writing through the session-scoped client so `auth.uid()`
reaches the audit trigger, and a Change history below — then add the sidebar entry so it is
reachable.

Purpose: ROADMAP SC1 — an admin sets the FY start in the settings area with no redeploy and the
FY/CY toggle immediately derives its boundaries from that value (D-10, D-11, D-12, D-13). Without
this plan the `app_settings` row created in 05-01 has no way to change and the Financial option on
the year toggle is permanently stuck at the 1 January default.
Output: `lib/settings/schema.ts`, the `/settings/general` route pair, the FY form, a reusable
audit-log empty message, and the nav entry.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser form -> `saveFinancialYearSettings` Server Action | An untrusted entry point callable directly, not only through the form |
| Server Action -> `app_settings` UPDATE | The only client-reachable write path to an org-wide setting |
| `app_settings` UPDATE -> `app_settings_audit` | The sole record of who moved every financial-year boundary (D-13) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-13 | Tampering | A direct `saveFinancialYearSettings` call bypassing client validation | high | mitigate | The action `safeParse`s with the same Zod schema before touching Supabase, and the `app_settings` `make_date(2001, ...)` CHECK rejects an impossible pair at the database even if both application layers were bypassed (two-layer validation, RESEARCH Pitfall 3). |
| T-05-14 | Spoofing | An unauthenticated caller invoking the Server Action | high | mitigate | `supabase.auth.getUser()` guard returns `Unauthorized` before any write; `app_settings` RLS grants update to the `authenticated` role only, so an anonymous PostgREST call is denied at the database too. |
| T-05-15 | Repudiation | An FY change with no attributable record | high | mitigate | The write uses the session-scoped client (never the privileged ingest writer), so `auth.uid()` resolves inside `trg_app_settings_audit` and the old-to-new row is written by a `SECURITY DEFINER` trigger the client cannot forge or suppress. |
| T-05-16 | Information Disclosure | Raw Postgres constraint names leaking into the form | medium | mitigate | `friendlyErrorMessage` maps the `make_date` CHECK violation to the UI-SPEC copy; the raw message is logged server-side only (WR-01, the `friendlyErrorMessage` precedent in the pricing action). |
| T-05-17 | Denial of correctness | A stale FY boundary rendered on metric pages after a save | medium | mitigate | `revalidatePath` for `/settings/general` plus all five metric routes in the same round trip, gated by a count check in the verify step. |
| T-05-SC | Tampering | npm/pip/cargo installs | low | accept | No package installs in this plan (05-RESEARCH Package Legitimacy Audit: not applicable). |
</threat_model>
