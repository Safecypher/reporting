# 08-02 — Tier-set supersede: tell the operator the whole truth

## Objective

Phase 5's CR-01 established the principle: an operator moving a tier set's `effective_from`
must be told which contract ends up pricing which days. The fix shipped for the case it was
written against and left two cases uncovered. Close both.

No file here overlaps 08-03, so the two run in parallel.

---

## Task 1 — WR-08: report the whole chain, not just the crossed neighbour

**File:** `lib/pricing/restate-scope.ts:101-159` (`resolveEditImpact`)

`atOrBeforeProposed` only considers sets with `effectiveFrom <= proposed`. A set *later* than
the proposed date is therefore never a candidate — including the set that ends up permanently
outranking the edited one.

The review's own worked example, which the tests should encode: sets `x` (2026-07-01),
`y` (2026-08-01), edited set `e` (currently 2026-09-01). Backdate `e` to 2026-07-15. `e` gains
07-15 to 07-31 from `x` (correctly reported), but from 08-01 onward `y` now outranks `e`'s new
earlier date **forever** — including every day from 09-01 that `e` exclusively owned before the
edit. `e` has surrendered its entire future pricing territory to a set the dialog never mentions.

Take option (b) from the review, not option (a). Walking the full chain of every set whose
territory changes produces a dialog that grows unboundedly with the number of tier sets and
buries the consequence that matters. Detecting the specific, nameable fact — *the edited set's
own former territory is now governed by something else* — is one extra sentence and is the
thing the operator actually needs to know.

Concretely: after the edit, determine whether days strictly after `max(current, proposed)` that
`e` previously governed exclusively are now claimed by another set. If so, surface that set as a
second named consequence alongside the existing `supersedes`.

`v_revenue_tier_set_by_day`'s rule is `order by effective_from desc limit 1` — governance is
"highest `effective_from` not exceeding the day". Derive from that rule; do not re-derive the
rule from the tests.

**Verify:**
```bash
npx vitest run lib/pricing/__tests__/restate-scope.test.ts
# The three-set backdate case is encoded, not just described
bash -c 'if grep -q "2026-07-15" lib/pricing/__tests__/restate-scope.test.ts; then echo "WR08_SCENARIO_ENCODED_OK"; else echo "WR08_SCENARIO_MISSING"; fi'
```

The new test must assert that the 2026-07-15 backdate names **both** `x` (crossed) and `y`
(absorbing the future), and that the single-set and already-governed cases still report no
second consequence — this must not fire spuriously on every edit.

## Task 2 — WR-02 / WR-09: the exact-date collision is a duplicate, not a restatement

**Files:** `components/pricing/pricing-tier-form.tsx` (both the create notice at `:420-426`,
`:334-341` and the edit dialog at `:384-393`)

When the proposed `effective_from` exactly equals an existing set's date, the dialog currently
renders *"Moving this tier set to 2026-09-01 makes it price days currently priced by the tier
set effective 2026-09-01"* — a sentence whose subject and object are the same date. The operator
confirms a restatement, and the server then rejects the write outright on
`pricing_tier_sets_effective_from_key` with a contradictory duplicate-date message.

**Fix this in the UI layer only.** `restate-scope.test.ts:274-282` deliberately pins the resolver
to report the collision, with a comment explaining that the resolver "must not pretend the
collision is harmless". That is a considered choice and it is correct — the resolver's job is to
describe governance, and the collision genuinely does change it. **That test must still pass
unchanged.** A fix that makes `resolveSaveImpact` return `null` here would contradict a
documented decision and is the wrong fix.

At both call sites: when `proposedEffectiveFrom === candidate.effectiveFrom` (create) or
`=== displaced.effectiveFrom` (edit), render a lightweight "a tier set already exists for this
date" hint instead of opening a restate confirmation. Reuse `PRICING_DUPLICATE_EFFECTIVE_FROM`'s
existing copy so the pre-submit hint and the post-submit server error say the same thing — the
operator should never be told two different stories about one condition.

Record the copy in a Copywriting Contract note following 07-UI-SPEC.md's convention.

**Verify:**
```bash

# The deliberate resolver pin is untouched
bash -c 'if grep -q "reports a displacement even when the proposed date lands exactly on another set" lib/pricing/__tests__/restate-scope.test.ts; then echo "RESOLVER_PIN_PRESERVED_OK"; else echo "RESOLVER_PIN_REMOVED_INVESTIGATE"; fi'

npx tsc --noEmit && npm test && npm run build
```
