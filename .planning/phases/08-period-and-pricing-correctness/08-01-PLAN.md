# 08-01 — Tracer: the data-window floor holds, end to end

## Objective

One vertical slice proving that no period, on any path, can resolve a `start` below
2026-08-13, and that no fetcher can be talked into reading below its own floor. This is the
tracer: it establishes the single source of truth, the clamp, and the no-regression proof
that every later plan in this phase leans on.

## Why this is one plan and not three

WR-03, WR-04 and the TypeScript half of WR-07 all land in `lib/dashboard/period.ts` and the two
fetchers. Splitting them would mean three plans editing the same three files, which is exactly
the overlap that makes parallel execution unsafe and rebases painful. IN-04 is folded in
because it is a comment in `card-inventory.ts`, a file this plan already touches.

---

## Task 1 — `lib/dashboard/data-window.ts`, the leaf module

Create the single source of truth. **It must have no `@/` value-imports and no imports at all
beyond TypeScript types.** `card-inventory.ts:220-227` documents the reason: this repo has no
vitest alias config, so a value-import through the `@/` alias resolves under `next build` but
throws under `vitest run`. A leaf module with zero imports cannot hit that.

Export, at minimum:

- `DATA_WINDOW_START` — `"2026-08-13"`, the calendar-date form
- `DATA_WINDOW_START_TS` — `"2026-08-13T00:00:00Z"`, the timestamptz form
- `clampToDataWindow(date: string): string` — returns `date < DATA_WINDOW_START ? DATA_WINDOW_START : date`, operating on `YYYY-MM-DD` strings by lexicographic comparison (valid for ISO dates, and the convention `rowsWithin` already uses)

Document in the module header that the SQL side has its own copy (`data_window_start()`,
added in 08-03) and that the two must be changed together — a shared constant in one language
is not a shared constant across the wire.

Then repoint the **dashboard cluster** at it by relative import:
`period.ts:53`, `bucketing.ts:30`, `card-inventory.ts:218,228`, `verification-drill.ts:15`,
`alignment-status.ts:88`. Keep each module's existing export names as re-exports where other
code imports them, so this task moves the definition without renaming anyone's import.

**Explicitly out of scope, and say so in the module header:** the six `lib/ingestion/normalise*`
files hold the floor as `Date.parse("2026-08-13T00:00:00Z")` — a number, used at parse time, on
a code path this phase does not otherwise touch. Consolidating those is a separate low-risk
sweep. Naming the deferral is the point; silently leaving them makes the next reader think the
consolidation is complete when it is not.

**Verify:**
```bash
# The leaf module imports nothing (the vitest-alias constraint, enforced not just documented)
awk '/^import /{print "IMPORT_FOUND: " $0; f=1} END{ if (!f) print "LEAF_MODULE_OK" }' lib/dashboard/data-window.ts
# The dashboard cluster no longer defines the literal itself
bash -c 'n=$(grep -l "\"2026-08-13" lib/dashboard/*.ts | grep -v data-window.ts | wc -l); [ "$n" -eq 0 ] && echo "DASHBOARD_CLUSTER_CONSOLIDATED_OK" || { echo "STILL_DUPLICATED:$n"; grep -l "\"2026-08-13" lib/dashboard/*.ts | grep -v data-window.ts; }'
# The deferred ingestion cluster is still there and still six files — a changed count means scope drifted
bash -c 'n=$(grep -lc "2026-08-13" lib/ingestion/normalise*.ts | wc -l); echo "INGESTION_DEFERRED_COUNT:$n"'
npx tsc --noEmit
```

## Task 2 — clamp the financial-year branch, AND the two fetchers

**WR-03, both halves.** Do both. Clamping only the resolver fixes today's single caller and
leaves the fetchers structurally willing to read below the floor for any caller added later —
the shape of fix that passes review and reopens six months on.

*Resolver half.* In the `yearMode === "financial"` branch of `resolvePeriod`
(`period.ts:329-334`), clamp the returned `start` through `clampToDataWindow`. Clamp `start`
only — `end` is an exclusive upper bound and is not floored by anything.

Keep the label honest. The scope badge renders the FY's true calendar span
(`FY2026-27 (6 Apr 2026 - 5 Apr 2027)`), and that span is a fact about the financial year, not
about the data. Do not rewrite the label to the clamped date. If the clamp actually bites, the
figures cover less than the label's span, and the UI should say so rather than silently implying
full coverage — surface it the way the existing partial-coverage captions do, and record the
copy in a Copywriting Contract note consistent with 07-UI-SPEC.md's conventions.

*Fetcher half.* In `verification-drill.ts:59` and `card-inventory.ts:308`, replace the ternary
with a clamp so the caller's range narrows within the floor instead of replacing it:

```ts
.gte("created_at", `${clampToDataWindow(range?.start ?? DATA_WINDOW_START)}T00:00:00Z`)
```

Both fetchers must end up unable to emit a `gte` below the floor for **any** input, including a
range whose `start` predates it.

**Verify:**
```bash
# No ternary-replacement of the floor survives in either fetcher
bash -c 'if grep -nE "range \? .range\.start|range\.start.*: *(DATA_WINDOW_START|REMOVED_CARDS)" lib/dashboard/verification-drill.ts lib/dashboard/card-inventory.ts; then echo "TERNARY_REPLACEMENT_STILL_PRESENT"; else echo "FETCHER_FLOOR_ANDED_OK"; fi'
# Both fetchers route their lower bound through the clamp
bash -c 'a=$(grep -c clampToDataWindow lib/dashboard/verification-drill.ts); b=$(grep -c clampToDataWindow lib/dashboard/card-inventory.ts); [ "$a" -ge 1 ] && [ "$b" -ge 1 ] && echo "BOTH_FETCHERS_CLAMPED_OK:$a,$b" || echo "FETCHER_CLAMP_MISSING:$a,$b"'
npx vitest run lib/dashboard/__tests__/period.test.ts lib/dashboard/__tests__/data-window.test.ts
```

Tests must cover, at minimum: an FY start of 6 April 2026 resolving `start === "2026-08-13"`
(the clamp biting); an FY start of 1 September 2026 resolving its own date unclamped (the clamp
not over-reaching); and a fetcher handed `range.start = "2026-01-01"` still issuing its `gte` at
the floor.

## Task 3 — WR-04: resolve the current year like every other year

Replace the wall-clock special case at `period.ts:331-332` so the current year derives its FY
bounds the same way every past year does — from 31 December of `of`, capped so the resolved
period never extends beyond `today`.

The bug to kill is that two loads of the same URL in the same UTC day can return different
bounds once the clock crosses the FY start day. After this, `resolvePeriod` must be a pure
function of `(params, fyStart, today)` with `today` mattering only for the cap, and the
current-year option must never duplicate an adjacent dropdown entry.

**Verify:**
```bash
# The wall-clock ternary is gone
bash -c 'if grep -n "of === currentUtcYearOf(today) ? today" lib/dashboard/period.ts; then echo "WALLCLOCK_TERNARY_STILL_PRESENT"; else echo "WR04_DETERMINISM_OK"; fi'
npx vitest run lib/dashboard/__tests__/period.test.ts
```

A test must assert that resolving the current-year FY period twice with two different `today`
values inside the same UTC day yields identical `start`/`end`, and that the resolved option does
not equal any adjacent dropdown option's bounds.

## Task 4 — IN-04, and the no-regression proof

*IN-04.* `rowsWithin`'s doc comment (`card-inventory.ts:153-161`) claims it serves both
`report_date` and `removed_at` callers; only `report_date` does. Add a `removed_at` test case
rather than narrowing the comment — the function genuinely is generic, and the comment is
describing intended contract, so the cheaper honest fix is to make the claim true.

*The proof.* This is the task that earns the phase its shape. Capture, before and after the
Task 2 and 3 changes, on the **same** live data:

| Figure | Where |
|---|---|
| $45,450 for 1,500,000 transactions | `tsys_msa_tier_test.sql` |
| D-06 invariant `1200.0000 > 1050.0000` | `tsys_msa_tier_test.sql` |
| August `projected_revenue` = daily sum = `5.58661764705882352965` | `revenue_forecast_test.sql` check 8 |
| September `projected_revenue` = daily sum = `578.26799999999999999100` | `revenue_forecast_test.sql` check 8 |

Record both readings in the SUMMARY. On current data the clamp should be a no-op — live rows
start at 2026-08-13, so the days the clamp removes hold nothing and contribute zero. **Say
whether that held, with the numbers, rather than asserting it.** Phase 7's IN-01 is the
precedent: the same "it can only be a no-op" reasoning was right there too, and it was still
worth proving with byte-identical before/after figures.

If a figure *does* move, stop and escalate rather than updating the expected value. A moved
figure means either the clamp is doing more than intended, or a previously verified number was
computed over days below the floor — and the second would be a finding larger than this phase.

**Verify:**
