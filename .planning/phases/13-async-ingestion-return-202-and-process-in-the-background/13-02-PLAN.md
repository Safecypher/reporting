<objective>
Correct a live correctness bug before anything is built on top of it.

Plan 13-01 shipped `PROCESSING_LEASE_SECONDS = 180` with a doc comment reasoning that the measured
worst case for a whole file is about 38 seconds, so 180 is several times longer than any attempt can
legitimately run. That reasoning was true for the synchronous design it was written for. D-07 moved
processing to a Netlify background function whose legitimate single attempt may run for 900 seconds,
and the same constant now hands a second claim to another caller at second 181 while the first writer
is still mid-file.

Purpose: ROADMAP SC-3 and INGEST-08. Idempotency is the whole of SC-3, and the claim function is the
mechanism that delivers it. A claim window shorter than the work it guards delivers the opposite.

Output: corrected constants with rewritten reasoning, an ordering test that gates them, migration 0049
moving the SQL default in lockstep, and the three inert columns documented in the catalog.
</objective>

    Ordering invariants, each asserted as its own case:
    - the lease window is strictly greater than the background-function ceiling.
    - the lease window exceeds the ceiling by at least the platform's documented invocation-retry
      delay, so a delayed invocation that starts late still holds a live lease when it finishes.
    - the sweepable age is strictly greater than the lease window.
    - the sweepable age is strictly greater than the background-function ceiling, stated as its own
      assertion even though it follows from the two above, because D-10 names it as a requirement in
      its own right and a future edit could satisfy the chain while breaking this.
    - the stuck age is strictly greater than the sweepable age.
    - the stuck age exceeds the whole worst-case retry saga: the attempt cap multiplied by the lease
      window is comfortably shorter than the stuck threshold, so the alert cannot fire at a file that
      is still legitimately retrying.
    - every one of these compares exported names against exported names. A literal number on either
      side of any of these assertions is itself the defect.

    `isSweepable`, extended with the attempt cap:
    - a row with no lease, old enough, and attempts below the cap is sweepable, exactly as today.
    - a row identical to it but with attempts equal to the cap is NOT sweepable.
    - a row with attempts above the cap is NOT sweepable.
    - the cap is checked independently of the lease: a capped row with a live lease is still not
      sweepable, and so is a capped row with no lease.
    - `resolvePendingState` is unchanged by the cap. A capped row past the stuck age still resolves
      as stuck, which is the whole point — the cap stops the retrying, not the reporting.

    Boundary behaviour at the new lease window:
    - a lease taken exactly the ceiling's worth of seconds ago is still live.
    - a lease exactly `PROCESSING_LEASE_SECONDS` old is NOT live, matching the SQL function's
      strictly-less-than comparison, unchanged from 13-01.

    measured worst case. An attempt count above one therefore means a previous attempt genuinely
    failed, and four is one real attempt plus three retries. State the arithmetic that makes four safe

    eighty minutes of wall clock, comfortably inside six hours, so the alert never fires at a file that
    is still retrying.

    file converging across chained attempts under a ~26-second ceiling — that world is gone. The number

    legitimate retry saga the cap permits, and shorter than the gap between daily drain runs, so a file
    that arrived this morning and is still pending at 16:00 UTC genuinely failed.

    Then extend `isSweepable` with the attempt cap: a row at or past `MAX_PROCESSING_ATTEMPTS` is not

    should stop being retried, but it must not stop being REPORTED — it is exactly the file the stuck
