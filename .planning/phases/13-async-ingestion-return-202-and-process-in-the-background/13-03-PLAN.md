<objective>
Cut the seam, without anything outside being able to tell.

`ingest()` today runs one pipeline from hashing to finalize. This plan splits it where the cost
splits — at `recordFile` — into a cheap claim and an expensive process, and gives the writer the one
new capability a two-process pipeline needs: the ability to write rows against a file id it did not
itself record.

Nothing changes behaviour yet. `/api/ingest` still calls `ingest()`, the drain still calls `ingest()`,
and both still do the whole thing in one request. That is deliberate: this plan is the structural half,
proven entirely by unit tests, and 13-05 is where the new entry point actually takes over.

Purpose: ROADMAP SC-2 and SC-3, and the INGEST-11 promise that the push path sees no change. The
background function in 13-05 cannot exist until `processClaimedFile` and a resumable writer do.

Output: `claimFile`/`processClaimedFile` extracted from `ingest()`, a writer that can resume an
existing file id, the pending-file access primitives, and `runPendingFile` — the one place that turns
a file id into a finished ingest.
</objective>

    Rework `lib/ingestion/index.ts` into three exported functions. The logic moves; it does not change.

    `claimFile(input, deps)` takes today's lines from the sha256 down to and including `recordFile`, and
    returns a DISCRIMINATED union of three kinds: already-uploaded, unrecognised, and claimed. The first
    two carry a fully-formed ingestion result — the same objects today's early returns build. The third
    carries the ingested file id and the report type.

    The unrecognised-report-type branch stays inside `claimFile`, recording the file and finalizing it
    as failed exactly as today. This is a decision, not an oversight, and the code should say so: the
    202 body has no field for an immediate terminal failure, and there is no parsing work to defer for a
    file nothing will ever parse. Deferring it would hand the processing path one more case to
    special-case and would leave the row at pending, where the stuck-pending alert would later report a
    file that was never going to succeed as a failure to converge.

    `processClaimedFile(claim, deps)` takes everything from the handler lookup onward: the guarded parse
    with its failed-finalize, validate, normalise, upsert, finalize, and the result assembly. It looks
    its handler up from the registry by report type rather than receiving one, so the background
    function can call it with nothing but a report type from a database row.

    `ingest(input, deps)` keeps its exact signature and becomes the composition: claim, return the
    terminal result for the two non-claimed kinds, otherwise process. Its doc comment keeps the
    single-shared-entry-point paragraph and gains a sentence saying the function is now a composition
    and why the push/drain path still calls only this in this plan.

    Put the claim-outcome type next to the ingestion result type in `lib/ingestion/types.ts`, so the
    contract lives with the rest of the contract.

    Then create `lib/ingestion/pending-runner.ts`, the one place that knows how to take a file id and
    turn it into a finished ingest. Export `runPendingFile(fileId, access, makeWriter)` where the access
    is the pending-file-access shape and the writer factory builds the resumed writer — both injected,
    so the runner is unit-testable with no Supabase client, exactly as the drain core is.

    The order inside it is the whole safety argument and must not be rearranged: load the row; if it is
    absent, missing; if its report type or storage path is null, not-processable; CLAIM; if the claim is
    refused, not-claimable and stop; only then download the bytes; build the resumed writer; call
    `processClaimedFile`. Wrap the work after the claim in a try/catch whose catch releases the claim and
    reports errored — a failed attempt that holds its lease for twenty minutes delays the retry for no
    reason, and releasing explicitly is cheaper than waiting the lease out.

    Why the runner is a module rather than code inside the background function: 13-05's function file is
