<objective>
Make a stuck upload visible on the page where someone would look for it.

This phase turns pending from a rare crash artefact into the normal intermediate state of every
upload. That creates a new failure mode — a file that enters pending and never leaves — and D-03
requires it be surfaced on two surfaces. This plan is the one on the screen: `/uploads` itself, for the
person reviewing days later with no Slack history to hand.

Purpose: ROADMAP SC-4 and INGEST-10. Five rows sat unnoticed before 2026-10-05, the oldest for three
days, and the plain Pending badge is exactly why nobody saw them.

Output: a pending-state derivation in `lib/upload/history.ts`, two new badge states in the uploads
history table, and the two columns the page must select to feed them.
</objective>

  <behavior>
    New cases in `lib/upload/__tests__/history.test.ts`, written BEFORE the code. Every existing case
    must still pass with its body unedited.

    The ingested-file row type gains the lease timestamp and the attempt count, and the combined row
    type gains a pending state, a pending-since timestamp and an attempt count, each nullable.

    The merge, now taking an explicit evaluation instant:
    - a done upload row carries a null pending state — the field is meaningful only for a pending row.
    - a failed upload row carries a null pending state.
    - a rejection row carries a null pending state and a null attempt count; a refusal at the door was never pending.
    - a pending row uploaded two minutes before the instant, with no lease, reads as processing.
    - a pending row uploaded three days before the instant, with no lease, reads as stuck and carries a pending-since equal to its upload time.
    - a pending row uploaded three days before the instant whose lease was taken ten seconds ago reads as processing — it is genuinely being worked on in this moment.
    - the attempt count is carried through from the row for an upload and is null for a rejection.
    - the existing ordering, tie-break, source-label and count behaviour is unchanged for every one of these rows.

    The pending caption:
    - returns null for a row with no pending state — there is nothing to caption.
    - for a processing row on its first attempt, returns null; a bare processing badge says enough and a caption that adds nothing is noise.
    - for a processing row on a later attempt, returns a caption naming the attempt number, because under a design where a healthy file succeeds in one attempt, a second attempt means the first failed.
    - for a row stuck since three days ago, returns a caption naming the duration in whole days.
    - for a row stuck since eight hours ago, returns a caption naming the duration in whole hours.
    - the caption never contains a raw ISO timestamp and never contains a negative duration, including when the instant is marginally before the upload time. Clock skew between a server render and a stored value is real and must not render as a negative age.
  </behavior>

  <action>
    Extend the ingested-file row type with the two new columns and the combined row type with the three
    derived fields. The row type is the shape the page's select produces, so adding the columns here is
    what makes the missing-column failure a type error rather than a silent degradation.

    Give the merge a required evaluation instant, not one defaulted to the current time. A default would
    make the function read the clock, which is exactly what stops it being testable at a boundary and
    lets a server render and a later client re-render disagree about whether a row crossed the six-hour
    line. The caller passes one instant and every row in that render is resolved against it.

    Inside the upload-row mapping, call `resolvePendingState` from `lib/ingestion/pending-state.ts` with
    the row's status, upload time, lease and attempt count, and the instant. Carry the result, the
    upload time as the pending-since when the state is stuck, and the attempt count. The rejection
    mapping carries nulls for all three — explicitly, not by omission, so the shape is uniform and the
    component never has to ask which kind of row it is holding.

    Importing from `lib/ingestion/pending-state.ts` here is deliberate and safe: that module is pure, has
    no Supabase or Next import, and is the single place the stuck threshold lives. The alternative — a
    second six-hour constant in this file — is precisely the drift that would let the page and the Slack
    alert disagree about what stuck means, and 10-03 established that discipline for the same reason on
    the freshness side. It matters more than usual this wave, because 13-02 is moving the values in that
    module while this plan is being built; importing means this plan inherits the corrected numbers with
    no edit.

    Add a pending-caption formatter returning a string or null, next to the existing count and
    source-label formatters, because it is the same kind of rule: a presentation decision that must be
    testable without a DOM.

    For a processing row, caption only the attempt number and only when it is above one. For a stuck
    row, caption the elapsed time since the pending-since in whole days when that is at least one day,
    in whole hours otherwise, with correct singular and plural forms. Clamp the elapsed value at zero
    before formatting, so a row whose stored timestamp is marginally ahead of the render instant reads
    as the smallest duration rather than a negative one.

    Keep every string in this module rather than in the component — that is what this file is for, and
    the dropzone's copy already lives in its sibling module for the same reason.
  </action>

    because a file being worked on is not a problem and must not read as one. Reuse the existing outline
    variant with the muted-foreground class already there rather than introducing a new colour token;
    there is no new semantic here, only a new word.

    Stuck: the destructive treatment the Failed branch already uses — the same border, background and
    text tokens. This is deliberate and matches how the table already distinguishes a refusal from a
    parse failure: same visual weight, different label. A file stuck for three days is a problem of the
    same order as one that failed to parse, and inventing a third severity for it would be a distinction
    without a difference.

    Keep the branch order and the existing three branches byte-identical in behaviour. A row whose
    pending state is null and whose status is none of the three known values still needs an answer —
    render the processing badge as the conservative default, never the stuck one. Guessing stuck for an
    unknown state would manufacture an alarm from missing information.

    already uses for a rejection's reason. One pattern for a secondary explanatory line on this table,
    not two.

    pass an evaluation instant into the merge. Take that instant once, before the merge, and use it for
    every row.
