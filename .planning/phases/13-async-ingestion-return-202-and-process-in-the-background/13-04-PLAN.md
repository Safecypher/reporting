<objective>
Close the loop the user actually sees. The server now accepts a file in milliseconds and finishes it
elsewhere; the browser has to stop reporting that as a failure and start reporting what really
happened.

Purpose: ROADMAP SC-1 and INGEST-07. The measured defect was never that the data was lost — it landed
perfectly, 41,239 rows accepted. The defect was that the screen said otherwise, and a user who
believes that re-uploads, or assumes a reporting gap. This plan is where that stops being true.

Output: a fourth batch outcome kind, a fire-and-forget dispatch after the 202, a bounded status
follow, and a small endpoint for the follow to read.
</objective>

    Change `uploadOne` to branch on a 202 before it does anything else with a successful response. On
    202 it reads the `fileId` and `reportType` from the body, dispatches the processing request, and
    returns the pending outcome. On any other ok status it behaves exactly as today, parsing an
    `IngestionResult` and returning the result outcome — that is the already-uploaded and unrecognised
    path and it must not change.

    Dispatch with `fetch` to the processing route, POST, `keepalive: true`, a JSON content type and a
    body carrying the file id. Do NOT await it. `keepalive` is what makes it survive the tab being
    closed between dispatch and the server's acknowledgement; an ordinary un-awaited fetch looks
    identical in the source and silently loses that property, which is the whole reason the research
    singled it out. `sendBeacon` is ruled out: no reliable JSON content type and no visibility at all
    into whether dispatch happened.

    Attach a catch to the dispatch that logs and does nothing else. A failed dispatch MUST NOT change
    the outcome. D-01 designed this trigger to be unreliable — a closed tab before the fetch is queued
    sends nothing, and a connection reset before the server acknowledges is indistinguishable from
    success — and put the daily drain sweep behind it for exactly that reason. Say so in a comment, so
    a future reader does not "fix" the silence by surfacing it as an error.

    `uploadOne` must remain a total function. The 202 body might not be valid JSON; that rejection has
    to land in the same catch the existing code already relies on, which is what makes the batch's
    continue-on-failure behaviour structural rather than incidental.

    Leave the drop loop sequential — `for` with an `await`, one request in flight. Add a line to its
    doc comment recording what changed and what did not: the loop now finishes almost instantly
    because each request is only a 202 round trip, so several files can be processing concurrently in
    the background where the slow synchronous request used to serialise them. That is accepted
    deliberately. At this project's stated volume of six reports a day a handful of concurrent
    background parses is not a load problem, and a client-side pacer would be machinery for a volume
    that does not exist — the same reasoning REQUIREMENTS.md already uses to reject a retry state
    machine for the inbox. If volume ever grows materially, this comment is where the decision is
    recorded and where it would be revisited.

    Then add the follow. After the batch completes and the toast is shown, collect the ids of the
    pending outcomes and poll the status endpoint until every one of them has left `pending` or the
    attempt budget runs out. Poll on a fixed interval of a few seconds, with a stated total bound of a
    few minutes — the measured worst case for one file is under a minute, and several files processing
    concurrently should still settle well inside that. Both numbers are named constants at the top of
    the file with a comment saying where they come from.

    As each id settles, replace that file's pending outcome with a result outcome built from the
    returned status and counts, and update the rendered outcomes so the panel changes under the user.
    When a file comes back `failed`, it becomes a result outcome reporting that — a genuinely failed
    parse is a real failure and must be shown as one.

    When the budget runs out with files still pending, leave them as pending outcomes and say so
    honestly: still processing, check the upload history. Never failure copy. The client's patience
    running out is not evidence of anything about the file, and this is the precise sentence that
    would otherwise reintroduce the defect this phase exists to remove.

    Stop the follow if the component unmounts, and call `router.refresh()` once when the follow ends —
    settled or timed out — so the server-rendered history table below picks up the real rows and shows

    after the batch can move to this ending rather than being duplicated.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `POST /api/ingest/process` | A client-initiated request carrying a file id, authenticated by the same-origin session cookie travelling on a keepalive fetch. |
| Browser session → `GET /api/ingest/status` | An authenticated caller names up to twenty ids and reads their status. |
| `/api/ingest/status` response → rendered batch panel | Server-supplied status and counts are rendered per file. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-13 | Information Disclosure | `GET /api/ingest/status` | low | mitigate | The read uses the user's own RLS-bound client, not the secret key, and selects only the id, status, report type and four row counts — a strict subset of what `/uploads` already renders to the same session. A nonexistent id is simply absent from the array, so existence is not confirmed or denied by a distinct response shape. |
| T-13-14 | Denial of Service | the status follow loop | medium | mitigate | The poll runs on a fixed interval with a stated total bound of a few minutes and stops on unmount, so a page left open overnight cannot flood this site's own function budget. The id list is capped at twenty per request on the server side regardless of what the client sends. |
| T-13-15 | Input Validation | the `ids` query parameter | medium | mitigate | Ids are split, trimmed, filtered against the UUID pattern, de-duplicated and capped before any database access; a malformed entry is dropped rather than reaching PostgREST as a cast error. An empty resulting list answers 200 with an empty array rather than erroring. |
| T-13-16 | Repudiation | a dropped fire-and-forget dispatch | medium | accept | Accepted by design per D-01: the client trigger is explicitly allowed to be unreliable and the daily drain sweep (plan 13-06) is the convergence guarantee behind it. The dispatch failure is logged client-side but deliberately never surfaced as a file outcome, because surfacing it would report a file that is about to succeed as broken. The residual risk — a file whose dispatch is lost and which therefore waits for the next drain — is bounded by that sweep and surfaced by the stuck alert if it never converges. |
| T-13-SC | Tampering | npm/pip/cargo installs | high | mitigate | package-legitimacy gate + blocking human checkpoint for [ASSUMED]/[SUS]. This plan installs no package — the dispatch uses the browser's native `fetch` with `keepalive`, recorded as requiring no dependency in 13-RESEARCH.md's Standard Stack. |
