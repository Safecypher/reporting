<objective>
Move the row-writing out of the request and into something with a budget that fits it.

The measurement is in: this site cuts a synchronous function at about thirty seconds, and the worst
file takes about thirty-eight. No amount of restructuring a Route Handler fixes that. D-07 chose a
Netlify background function — 900 seconds, a 202 answered by the platform on invocation, and
`lib/ingestion` running unchanged inside it because it was built framework-agnostic on purpose.

This is the phase's tracer and its riskiest plan. It is the first thing in this repository to deploy a
hand-authored Netlify function alongside the Next.js runtime, the first to ask the function bundler to
swallow ExcelJS, and the first to authenticate a caller that has no session. Each of those is a
documented failure class rather than a certainty, so this plan ends by deploying and trying to break
it — the same way 13-01 ended by measuring rather than by citing documentation.

Purpose: ROADMAP SC-2, INGEST-06 and the first half of INGEST-08. The browser was told "Upload failed"
for 43,383 rows that landed perfectly. The request has to stop being the thing that must finish in
time.

Output: a `netlify.toml`, the background function, the shared trigger-and-verify module, `/api/ingest`
answering 202 and firing server-side, and a recorded deployed run proving all of it.
</objective>

    The secret verifier:
    - a presented bearer equal to the configured secret verifies.
    - a presented bearer differing in one character does not.
    - an empty or absent Authorization header does not.
    - a header without the bearer scheme does not.
    - an absent configured secret returns a distinct not-configured outcome rather than verifying — fail closed, never open, matching the drain route.
    - the comparison is performed over equal-length digests, so a presented value of a different length cannot throw instead of returning false.
    - no return value and no thrown error contains the secret or the presented token.

    The trigger:
    - with an origin, a secret and an injected fetch, it posts to the shared path constant with a bearer Authorization header and a JSON body carrying the file id, and reports a fired outcome.
    - it never throws. A rejecting fetch reports a failed outcome carrying a message; it does not propagate.
    - a non-2xx response reports a failed outcome rather than a fired one, so a caller can log the difference even though neither changes the caller's own answer.
    - an absent origin reports a not-configured outcome without calling fetch at all.
    - an absent secret reports a not-configured outcome without calling fetch at all.
    - the request carries an abort signal with a timeout, so a hung invocation cannot hold the caller open.
    - the failed outcome's message never contains the secret or the Authorization header.

  <action>
    **The shared module first.** Create `lib/ingestion/process-trigger.ts`. It holds three things and
    nothing else.

    A path constant naming the background function's invocation path, under Netlify's reserved
    functions prefix, with a doc comment stating the failure it exists to prevent: a POST to a path
    that does not route to a background-configured function returns 202 and silently never executes,
    which is documented community experience with this exact platform. One definition, read by the
    function's file name and by every caller, means a rename cannot half-happen.

    A verifier taking an Authorization header string and the configured secret, returning a small
    discriminated result: verified, unauthorized, or not-configured. Hash both sides first so the
    buffers compared are equal-length digests, then compare in constant time. Fail closed on an absent
    secret, exactly as the drain route does — an unset variable must disable the path, never open it.

    A trigger taking a file id and an injected set of dependencies — a fetch implementation, the target
    origin, the secret and a timeout — returning a discriminated result: fired, failed with a message,
    or not-configured. It never throws, under any input. Injecting fetch is what makes every case above
    testable without a network, and injecting the origin and secret is what keeps this module free of
    `process.env` so it stays as pure as the rest of `lib/ingestion`.

    The target origin is the site's canonical public origin. Read it from `NEXT_PUBLIC_SITE_URL` at the
    CALL SITE, not in this module — that variable already exists in this project precisely because a
    Netlify request reports a deploy-unique host rather than the public one, and this repository has
    been bitten by that before. Record the consequence honestly in the module's doc comment: because
    the origin is configured rather than derived, a branch deploy whose variable still points at
    production will invoke production's function. Since both share one database, the right file is still
    processed — but the logs land on the wrong deploy, and a reader chasing a missing invocation should
    know to look there.

    Keep both helpers in `lib/ingestion/` rather than `lib/push/`: the function imports them relatively,
    the directory is already gated free of Next.js imports and value alias imports by 13-03, and putting
    them anywhere else would widen the set of directories the bundler has to cope with.

    **Then the function.** Create `netlify/functions/ingest-process-background.mts`.

    Import everything through RELATIVE paths. The tsconfig alias is a compile-time construct the
    function bundler does not resolve, and this is the single most likely way to turn a working module
    graph into a failed deploy.

    Declare it a background function twice over: name the file with the trailing background suffix, and
    export a config object setting the background flag. The exported object is the form Netlify's
    current docs recommend for new functions; the filename suffix is the older form and still supported.
    Both say the same thing, neither conflicts with the other, and the documented failure mode here is a
    function that silently runs synchronously or not at all — so declaring it both ways costs nothing
    and removes one way to be wrong. Do NOT import the config type from `@netlify/functions`; the object
    needs no type to be read at build time, and declining the dependency keeps this phase's
    install-nothing fence intact.

    The handler, in this order and no other: read the configured secret from the environment; verify the
    Authorization header with the shared verifier and answer 401 on anything but verified and 500 on
    not-configured; parse the JSON body and validate that the file id is a well-formed UUID, answering
    400 if it is not — a malformed id must fail cleanly rather than reach the database as a cast error;
    then call `runPendingFile` with the pending-file access factory and a writer factory that builds a
    resumed writer for that id.

    Answer 200 for every outcome the runner can report, with a body naming which one. Not a 404 for a
    missing or unclaimable id: nobody reads this response — the platform already answered 202 to the
    caller long before the handler ran — and a non-2xx would only make a healthy idempotent no-op look
    like a failure in the platform logs. Say that in a comment, next to the reasoning that the empty
    202 is also why no outcome can ever be communicated back through this response: the only channel to
    the user is the `ingested_files` row the client follows.

    Log each outcome with the file id and, for the errored case, the error message. Never log the
    secret, any part of it, or the header it arrived in.

    Declare no runtime: Netlify functions run on Node by default, which is what ExcelJS needs, and D-06
    rules Edge out for this project on two independent grounds.

    **Then the configuration.** Create `netlify.toml` containing a functions block and NOTHING ELSE: the
    directory, the esbuild bundler pinned explicitly, and ExcelJS and PapaParse marked as external
    modules. The externals are a precaution against a documented esbuild failure class for CommonJS
    packages with conditional requires — exactly the shape of the dynamic ExcelJS import in
    `lib/ingestion/index.ts` — and marking a package external costs nothing if it turns out not to have
    needed it. Say in a comment that this is precautionary and that Task 3's deploy is what decides.

    Do not add a build block. This repository has deployed without a `netlify.toml` for its whole life,
    which means every build setting currently lives in the dashboard; introducing a build block here
    would silently override settings nobody in this plan has looked at. Do not pin the Next.js adapter
    plugin either — Netlify's own documentation says not to, and it auto-installs at build time.

    **Then the documentation.** Add the new secret to `.env.local.example`, following the

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the public internet to the background function | The function's path is outside Next's routing tree, so the proxy auth gate never sees it. Its own shared-secret check is the only authentication layer it has. |
| `/api/ingest` to the background function | A server-to-server HTTP call carrying a bearer secret, crossing the public origin because the function is invoked over HTTP. |
| Browser session to `POST /api/ingest` | Unchanged: an authenticated user uploads bytes. The browser never calls the background function. |
| Netlify environment to the function runtime | The secret and the Supabase credentials must carry the Functions scope to be readable at runtime. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-43 | Spoofing | the background function's HTTP endpoint | critical | mitigate | Fail-closed shared-secret auth, hashed on both sides and compared in constant time, mirroring the drain route exactly.
