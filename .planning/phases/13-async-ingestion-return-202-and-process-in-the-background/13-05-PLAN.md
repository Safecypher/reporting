<objective>
Make a file that cannot finish in one attempt finish anyway — and prove that doing so leaves the
audit numbers exact.

D-05's posture is to assume the worst: plan for a ~26 second synchronous ceiling against a measured
~38 second worst-case file, which means processing must converge across several attempts rather than
requiring one clean run. But D-05 also required the ceiling be measured first, because if it is
really 60 seconds then every mechanism in this plan is complexity nobody needed.

So this plan opens with the decision, and what it builds depends on the answer.

Purpose: ROADMAP SC-3 and INGEST-08. Two triggers that can race, on a file that may need several
goes, against a table whose counts are the thing the business trusts.

Output: either a single-attempt confirmation and a contention test suite, or that plus a resumable
chunk cursor, a bounded attempt and a self-continuation.
</objective>

    The contention tests use the existing in-memory fakes rather than a live database. The live proof
    that the claim function itself excludes a second caller was taken in plan 13-01 Task 3 against the
    real Postgres function; these tests pin that the APPLICATION honours the refusal — that it stops
    rather than carrying on, which is a different property and the one a code change could break.

    Record in the summary, in prose, what this design does to `rows_accepted` and `rows_duplicate`
    under each case, because the brief for this phase asked for it explicitly and because it is the
    number the business trusts:

    - **Two triggers racing.** The claim's conditional update matches zero rows for the loser, which
      therefore never parses, never writes and never finalizes. Exactly one writer finalizes. The
      persisted counts are correct by construction, not by de-dup absorbing a double write.
    - **One clean attempt.** Accepted plus duplicate equals the normalised row count, with rejected
      and excluded accounted separately — unchanged from today.
    - **Several chained attempts.** Every chunk is counted exactly once: as newly-written rows by
      whichever attempt committed it, or as duplicates by a later attempt that re-wrote it. The sum
      is therefore still exact.
    - **A function cut between a chunk's commit and its progress update.** That chunk's rows are
      counted as duplicates by the next attempt instead of as accepted. The sum is unaffected; the
      split moves by at most one chunk's worth of rows per interruption. This is the single
      inexactness the design admits and it is bounded, stated, and strictly preferable to the
      alternative — recording progress first would skip those rows entirely, which is silent data
      loss rather than an accounting wobble.
  </action>

    D-05 requires. Document the arithmetic where it is declared: the remaining budget has to cover the
    claim, the storage download, the parse, the finalize and the continuation dispatch, none of which
    are free, and an attempt that budgets the whole ceiling for writing is an attempt that gets cut
    before it can record where it got to.

    Give `createSupabaseWriter`'s options two more optional fields alongside `resumeFileId`: the
    starting cursor chunk and the running accepted and duplicate totals loaded from the row. They are
    only ever set together with a resume id, and the writer must ignore all of them when there is no
    resume id — that guard is what keeps the push/drain path byte-identical.

    Rework both chunked loops — the verifications one and the generic one — to the same shape. Skip
    the batches below the starting cursor without sending them. Before each remaining batch, check the
    deadline; if it has passed, set an interrupted flag and break. Send the batch. On success,
    accumulate the written count into the running accepted total and the batch's shortfall into the
    running duplicate total, then record the new cursor and both totals in one update.

    Record progress AFTER the batch commits, never before. This ordering is the whole correctness
    argument and deserves a comment saying why: a function cut between the commit and the progress
    update makes the next attempt re-write that chunk, where the de-dup absorbs it and it is counted
    as duplicates instead of accepted — the sum stays exact and only the split moves. Recording first
    would make the next attempt SKIP that chunk, and those rows would never be written at all. One
    extra single-row update per thousand rows is the price, against roughly a second of upsert work
    per chunk, and it buys an exact sum.

    Expose `wasInterrupted()` on the writer as an OPTIONAL member of `IngestDeps`, so every existing
    fake in the test suite keeps compiling and `processClaimedFile` treats its absence as false.

    In `processClaimedFile`, after the upserts, check it. When interrupted, return a result carrying
    an optional incomplete marker with the cursor reached, and do NOT finalize — the row stays
    `pending` and is the next trigger's to claim. When not interrupted, finalize as today, but first
    assert that the accepted and duplicate totals sum to the normalised row count; if they do not,
    finalize as failed with that discrepancy as the reason rather than persisting numbers that do not
    add up. A reconciliation tool that quietly writes a wrong total is worse than one that says it
    cannot.

    Make `runPendingFile` load the cursor and the running totals from the row it already reads, pass
    them into the writer it builds, and report the incomplete outcome with the cursor before and after
    so the caller can see whether progress was made.

    In the processing route, after an incomplete outcome, fire a continuation POST to this same route
    — `new URL` against the incoming request so the origin is the deployed one — carrying the file id
    and the `DRAIN_CRON_SECRET` bearer, since a server-to-server call has no session cookie. Do not
    await it.

    Guard the continuation with BOTH conditions, and fail closed on either: the cursor must have
    advanced, and the attempt count must be below `MAX_PROCESSING_ATTEMPTS`. An attempt that advanced
    the cursor by zero chunks re-firing itself is an infinite request loop against this site's own
    function budget, and a file that genuinely cannot be written must become a stuck row the alert
    reports, not a loop nobody notices. When either guard refuses, log the file id and the reason and
    return normally — the drain sweep will try once more tomorrow and the stuck alert will say so.

    Never log the bearer secret or any part of it.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-17 | Denial of Service | the self-continuation | high | mitigate | Two independent guards, both fail-closed: the cursor must have advanced since the previous attempt, and the attempt count must be below `MAX_PROCESSING_ATTEMPTS`. Either refusing ends the chain and leaves a `pending` row the stuck alert reports. An attempt making zero progress can never re-fire itself, which is the only shape that produces an unbounded loop. |
| T-13-18 | Information Disclosure | `DRAIN_CRON_SECRET` on the continuation | high | mitigate | Read from `process.env` inside the Node route handler, placed only in an outbound Authorization header to this app's own origin derived from the incoming request URL, never logged, never returned in a response body, never written to a database column. |
| T-13-19 | Tampering | the persisted audit counts across attempts | critical | mitigate | Progress is recorded only after a chunk commits, so an interrupted function re-writes rather than skips. Every chunk is counted exactly once, so the sum of accepted and duplicate is exact in all cases; only the split between them can move, by at most one chunk per interruption, which is stated in the code and in the summary. A finalize whose totals do not sum to the parsed row count finalizes as failed rather than persisting them. |
| T-13-20 | Tampering | two writers finalizing one file | high | mitigate | The claim admits exactly one caller; the loser never reaches a write. The resumed writer's finalize is additionally filtered on `status = 'pending'` (plan 13-02), so even a writer whose lease expired cannot overwrite a finished row's counts. |
| T-13-SC | Tampering | npm/pip/cargo installs | high | mitigate | package-legitimacy gate + blocking human checkpoint for [ASSUMED]/[SUS]. This plan installs no package — 13-RESEARCH.md's Package Legitimacy Audit records the phase as introducing no new npm dependency. |
