<objective>
Close the loop the user actually sees. The server now accepts a file in milliseconds, fires the work
itself and finishes it elsewhere; the browser has to stop reporting that as a failure and start
reporting what really happened.

Purpose: ROADMAP SC-1 and INGEST-07. The measured defect was never that the data was lost — it landed
perfectly, 41,239 rows accepted. The defect was that the screen said otherwise, and a user who believes
that re-uploads, or assumes a reporting gap. This plan is where that stops being true.

Output: a fourth batch outcome kind, a small status endpoint, and a bounded follow that replaces each
pending outcome with the real one.
</objective>

  <action>
    Change the upload helper to branch on a 202 before it does anything else with a successful response.
    On 202 it reads the file id and report type from the body and returns the pending outcome. On any
    other ok status it behaves exactly as today, parsing an ingestion result and returning the result
    outcome — that is the already-uploaded and unrecognised path and it must not change.

    It dispatches nothing. Under D-08 the server fired the processing trigger inside the same request
    that produced this 202, before the response left, so by the time the browser reads the body the work
    has already been started by something that holds a credential the browser does not and cannot. Put
    that in a comment where a reader would otherwise expect a fetch: the original design had the browser
    fire a keepalive request, and it was replaced because a bare Netlify function sits outside Next's
    routing tree and never sees the Supabase session cookie — so a browser-originated call would have
    needed a token minted for the hop, and would still have depended on the tab surviving. Firing
    server-side removes the closed-tab window entirely. A future reader who adds a client dispatch back
    is reintroducing an authentication problem, not restoring a feature.

    The upload helper must remain a total function. The 202 body might not be valid JSON; that rejection
    has to land in the same catch the existing code already relies on, which is what makes the batch's
    continue-on-failure behaviour structural rather than incidental.

    Leave the drop loop sequential — a `for` with an `await`, one request in flight. Add a line to its
    doc comment recording what changed and what did not: the loop now finishes almost instantly because
    each request is only a 202 round trip, so several files can be processing concurrently in the
    background where the slow synchronous request used to serialise them. That is accepted deliberately.
    At this project's stated volume of six reports a day, a handful of concurrent background parses is
    not a load problem, and a client-side pacer would be machinery for a volume that does not exist —
    the same reasoning REQUIREMENTS.md already uses to reject a retry state machine for the inbox. If
    volume ever grows materially, this comment is where the decision is recorded and where it would be
    revisited.

    Then add the follow. After the batch completes and the toast is shown, collect the ids of the
    pending outcomes and poll the status endpoint until every one of them has left pending or the
    attempt budget runs out. Poll on a fixed interval of a few seconds with a stated total bound. Size
    the bound against what is now actually possible rather than against the old measurements: a
    background function may legitimately run up to fifteen minutes, so a bound of a couple of minutes
    will sometimes expire on a genuinely healthy file — which is fine, because expiry is reported as
    still processing and never as failure. Say that in the comment, and say both numbers' basis, as
    named constants at the top of the file.

    As each id settles, replace that file's pending outcome with a result outcome built from the
    returned status and counts, and update the rendered outcomes so the panel changes under the user.
    When a file comes back failed, it becomes a result outcome reporting that — a genuinely failed parse
    is a real failure and must be shown as one.

    When the budget runs out with files still pending, leave them as pending outcomes and say so
    honestly: still processing, check the upload history. Never failure copy. The client's patience
    running out is not evidence of anything about the file, and this is the precise sentence that would
    otherwise reintroduce the defect this phase exists to remove.

    Stop the follow if the component unmounts, and refresh the router once when the follow ends —
    settled or timed out — so the server-rendered history table below picks up the real rows and shows
    13-04's processing or stuck badges for anything still in flight. The existing single refresh after
    the batch can move to this ending rather than being duplicated.
  </action>
