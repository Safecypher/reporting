# Phase 4 — UI Design Contract

> Visual and interaction contract for Reconciliation & Discrepancy Flagging. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope:** `/reconciliation` page with two sections — Billing-vs-Verification daily flags (RECON-01) and Card-Inventory reconciliation incl. APIGEE cross-check (RECON-02, DASH-02) — each flag row showing status + delta (RECON-03) and drilling into the Phase 3 `DrillSheet` (DASH-03 reuse, L-01).
>
> **Standing contract:** This phase does **not** invent a new visual language. It is a **strict extension** of `.planning/phases/01-end-to-end-spine/01-UI-SPEC.md` (brand tokens, shadcn→brand mapping, 4-state contract, copy voice) and `.planning/phases/03-revenue-sla-drill-down/03-UI-SPEC.md` (drill-down Sheet mechanics, dense-table conventions, `.metric` KPI treatment). Only what is new to Phase 4 — status badges (OK/mismatch/needs-review), signed-delta formatting, the two-section reconciliation page, and the "pending" first-class state — is specified below. Where this document is silent, defer to 01-UI-SPEC.md then 03-UI-SPEC.md, in that order.

## Design Aesthetic (Decision)

**Decision:** Unchanged from Phase 1/3 — clean, professional, trustworthy internal-tool aesthetic, Cypher Blue as the single lead, 1pt hairlines over shadows, pill buttons, calm neutrals so colour carries meaning. Phase 4 introduces the brand's **full three-state semantic system** (`--success` / `--warning` / `--error`) for the first time at this density — every reconciliation row carries one of exactly three statuses, so restraint and consistent badge treatment matter more here than in any prior phase. This is the demo centrepiece: it must read as calm and trustworthy, not alarming — "pending" is the expected steady-state for the most recent day, not a warning to react to.

**Rationale:** PROJECT.md's core value is *trustworthy reconciliation* — the visual system's entire job on this page is to make "are we balanced?" scannable in one glance without crying wolf. D-03's "pending is not an error" decision is the single most important nuance the visual contract must protect: pending uses `--warning` styling but calmer copy/iconography than a true mismatch, both using `--warning`/`--error` distinctly, never conflated.

## Visual Hierarchy & Focal Points

| Screen | Primary anchor (focal point) | Secondary anchors | Tertiary / chrome |
|--------|------------------------------|-------------------|-------------------|
| **Reconciliation page** | The **Billing-vs-Verification table** (top section, first thing the eye meets — this answers the core-value question "does billing equal verifications?") | The **Card-Inventory table** (second section, below a `separator`) — enrolled/unenrolled/live-count summary row above its own per-day flag table | The APIGEE cross-check sub-table (nested within Card-Inventory section, visually subordinate — amber-only signal per D-10, never competes with the two hard-flag tables); freshness badge; missing-report-day gap banner if present |
| **Billing-vs-Verification section** | Per-day rows: status badge + signed delta, most-recent day visually distinguishable as "pending" (not alarmed) | Section heading with a one-line summary count ("2 days need review") | Column headers (Date, Billing count, Verification count, Delta, Status) |
| **Card-Inventory section** | Per-day rows: status badge + signed delta (inventory drop vs removed-cards tally) | Live-count / enrolled / unenrolled summary strip above the table (three small `.metric`-style numbers, smaller scale than Revenue's headline KPI — this page has no single "hero number", it has a hero *table*) | APIGEE cross-check sub-rows (amber badges only); missing-snapshot-day gap rows (distinct visual treatment — see Color) |
| **Drill-down Sheet** (reused from Phase 3) | The TanStack Table of contributing raw rows (billing/verification/inventory/removed/APIGEE, per the flag drilled), split by source table if more than one contributes | Sheet header stating exactly what's being drilled (e.g. "Billing vs Verification — 20 Aug 2026, mismatch") | "Copy link" affordance, unchanged from Phase 3 |

**No single `.metric` headline KPI this phase** (unlike Revenue/SLA) — reconciliation's value is in the *table of daily statuses*, not one number. The live-card-count, enrolled, and unenrolled figures use a smaller secondary numeric treatment (18–20px Poppins Bold, not the 48px `.metric` display) so they read as supporting context for the Card-Inventory table, not a competing hero.

## Color

Unchanged palette from 01-UI-SPEC.md/03-UI-SPEC.md (60/30/10, Cypher Blue lead, brand semantic tokens). Phase 4 is the first phase to use **all three semantic status tokens together** in one table — the reserved-for list below is binding and must not be reinterpreted per-row.

| Role | Token | Value | Usage (Phase 4, binding) |
|------|-------|-------|----------------------------|
| OK / balanced | `--success` (bg `--success-bg`, border `--success-border`) | `#0a7a4b` / `#e6f6ee` / `#b9e3cd` | Status badge only, when billing count = verification count (settled) or inventory drop = removed-cards tally |
| Needs-review / pending | `--warning` (bg `--warning-bg`, border `--warning-border`) | `#8a6d00` / `#fff6d6` / `#f0dc95` | Status badge for: (a) most-recent day awaiting D+1 settling (D-03 "pending"), (b) all APIGEE cross-check divergence rows (D-10 — always amber, never escalated to error), (c) missing-snapshot-day gap rows (D-07) |
| Mismatch (confirmed) | `--error` (bg `--error-bg`, border `--error-border`) | `#c1121f` / `#fde8e8` / `#f2bdc0` | Status badge **only** for a settled (past D+1), unresolved count discrepancy — billing≠verification or inventory-drop≠removed-tally. Never used for pending or APIGEE divergence (D-10, D-03 — reserving red exclusively for confirmed mismatches keeps trust in the hard flags). |
| Lead accent (~10%) | `--cypher-blue` | `#382aff` | Active "Reconciliation" nav item, section headings' underline rule (if used), the Copy-link/drill affordances inherited from Phase 3 — **not** used on any status badge (badges are exclusively success/warning/error, keeping brand-blue reserved for navigation/action, never conflated with a data-status meaning) |
| Neutral row background (settled/OK rows) | `--bg-1` | `#ffffff` | Default row background — OK rows get **no** tinted background, only the badge carries colour, so a long table of mostly-OK rows stays calm and the few flagged rows pop |
| Delta magnitude text | `--fg-1` | `#37373a` | The numeric delta itself is neutral ink, not colour-coded — colour lives in the badge only, per the brand's "colour carries meaning, not decoration" principle (01-UI-SPEC.md) |

**Binding rule:** a status badge's color is fully determined by the status enum (`ok` / `needs_review` / `mismatch`) computed in the DB view (L-03) — the UI never infers colour from the delta sign or magnitude directly. This keeps the correctness verdict (SQL) and its visual representation (badge) in lockstep, which matters for a trust tool.

## Interaction & State Contract (trust-critical)

Every data surface on `/reconciliation` implements the **same 4-state contract as Phase 1/3** — no exceptions:

1. **Loading** — skeleton placeholder rows in both table sections, never a blank flash.
2. **Empty** — explicit empty-state copy with a next action (link to Upload), shown only when *none* of the four contributing sources (billing, verification, inventory, removed-cards) have any data yet.
3. **Populated** — data with the `Data as of last import: {timestamp}` freshness badge and data-window caption, matching Phase 1/3 placement exactly. Populated has a **good-news micro-state** (all rows OK/no flags) distinct from populated-with-flags — phrase positively per Copywriting, mirroring the SLA breach-table precedent (03-UI-SPEC.md).
4. **Error** — explicit error copy, never swallowed. A reconciliation computation failure (e.g. a view query error) is an error state, never rendered as a silently-empty or silently-all-OK table — **a trust tool must never look "clean" because it failed to check**.

**Pending is a first-class status value, not a loading/error state (D-03, binding):**
- The most-recent business day's row(s) show the `needs_review`/pending badge with the pending-specific explainer copy ("Awaiting {date}'s counterpart report...") — this must read calmly, not as an alarm. Do not use the same iconography/urgency as a confirmed mismatch.
- Only a day that remains unresolved *after* its D+1 settling window has passed escalates visually to the `mismatch` badge.

**Missing report-day gaps (D-07, binding):**
- A day with no `card_inventory` snapshot is rendered as its own row style — distinguishable from both a flagged discrepancy and a normal OK row (e.g. dashed row border or muted `--fg-3` text with the `--warning` badge) — communicating "we don't know" rather than "it's fine" or "it's wrong". Never silently skip the day from the table.

**APIGEE cross-check (D-10, binding):**
- Always rendered as `--warning` (needs-review), regardless of the divergence's direction or magnitude — it never becomes `--error`/mismatch in v1. Visually subordinate to the two hard-flag tables (smaller, nested/collapsed-by-default acceptable if the planner chooses, but must remain reachable, never hidden entirely).

**Drill-down contract (reused verbatim from Phase 3, D-10/D-11/L-01):**
- Every flag row is clickable and opens the Sheet via URL query params (drill state derives from the URL, not component state).
- Closing the Sheet uses replace-state to strip drill params, matching Phase 3 exactly.
- The Sheet header always states what filter produced its contents (date + status + entity).
- For a billing-vs-verification flag, the Sheet shows the contributing rows from **both** sources (billing rows and verification rows for that day) — plan for a way to visually separate the two sets within one Sheet (tabs, stacked sections with sub-headings, or a combined table with a source-type column — planner's call, but the separation must be explicit, never merged into one ambiguous list).

Focus rings (brand `--focus-ring`) visible on all interactive elements, including status badges/rows that trigger the drill Sheet (must be keyboard-operable, not click-only) — unchanged rule from Phase 1/3.
