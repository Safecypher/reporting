## Design Aesthetic (Decision)

**Decision:** Unchanged brand aesthetic — Cypher Blue as the single lead, 1pt hairlines over
shadows, calm neutrals so colour carries meaning. Phase 7 introduces one genuinely new visual
problem, and resolves two tensions the context left for this document to reconcile:

1. **A number that is not yet real must never be mistaken for one that is.** The projected
   figure sits directly beside the actual figure, in the same currency format, at a similar
   reading position — the exact conditions under which a screenshot misreads a forecast as a
   booked number. The answer is not a new alarm colour (a forecast is not a warning) but a
   **provenance treatment**: muted ink, a smaller size than the hero `.metric`, and — the one
   genuinely new piece of visual grammar — an **outlined, dashed card border**. This app already
   uses a dashed border to mean "not a definitive state" (`EmptyState`/`PeriodEmptyState` render
   `border-dashed border-border`); the projected tile reuses that exact idiom, tinted with the new
   `--provisional-border` token instead of the neutral `--border`, so it reads as a member of the
   same family ("this box is not the same kind of fact as its neighbour") without inventing a
   second visual language for the same idea.
2. **D-10 (Bit Addict leads, TSYS shown alongside) and D-16 (two adjacent tiles: "Revenue to
   date" / "Projected month-end") name two different pairings that must coexist without becoming
   a four-way KPI row.** Resolved by nesting: the "Revenue to date" tile is the **outer** pairing
   member (vs. "Projected month-end") and **internally** contains the Bit Addict headline plus
   the smaller TSYS figure and variance phrase. TSYS never gets its own full tile — it is
   subordinate content inside the actual-to-date tile, exactly as D-09 requires ("Bit Addict is
   the headline revenue figure... never averaged in").

**Rationale:** Roadmap success criterion 1 requires the actual/projected distinction to be
unmistakable at a glance; success criterion 2 requires the per-source disagreement to be visible
rather than averaged away. Both must hold simultaneously on one page without the KPI row growing
to four cards, which would dilute the very "at a glance" property both criteria depend on.

**Actual/projected KPI pair internal hierarchy (binding, the core of this phase's visual
contract):**

*"Revenue to date" (actual) card:*
1. Eyebrow label — `Revenue to date` (12px, unchanged `CardTitle` treatment).
2. **Headline figure** — Bit Addict revenue, 48px Cypher Blue `.metric` with its existing
   Cypher-Blue underline (unchanged from `revenue-kpi-cards.tsx`).
3. **TSYS secondary block** — a 12px uppercase `TSYS` side label (`--fg-3`, identical treatment
   to `PairedMetricCard`'s side labels), the TSYS figure at 14px (**not** the 20px "paired
   figure" size used on `/alignment` — see Design Aesthetic point 2, this figure is deliberately
   smaller than its `/alignment` counterpart because here it is subordinate, not equal), and the
   delta/which-side-short phrase beneath it, reusing 06-UI-SPEC.md's exact phrase grammar and
   zero-denominator em-dash handling, formatted as currency instead of a count.

*"Projected month-end" / "Projected year-end" (projected) card:*
1. Eyebrow label — `Projected month-end` (current-month scope) or `Projected year-end`
   (current-year scope). Absent entirely (see below) for every other scope.
2. **Point figure** — 20px, `--provisional` ink, bold tabular-nums (reuses the 20px "secondary
   numeric" size 06-UI-SPEC.md established, deliberately smaller than the 48px hero so the two
   cards never read as equivalent even before colour/border are considered).
3. **Band sentence** — 14px, `--fg-2`: *"If the rest of {the month/the year} runs at our
   quietest day's pace: {low}. At our busiest day's pace: {high}."* (D-05's own explainability
   test, rendered verbatim as the band's copy — if an implementation cannot produce this sentence
   honestly, the projection logic has drifted from D-05).
4. **Permanent method caption** — 12px, `--fg-3`, always visible, never a tooltip (D-17):
   *"Projected from {n} covered days {this month/year-to-date} at {rate}/day (as at
   {asOfDate}); {m} uncovered day(s) inferred at the same rate."*
5. **Honest-degradation state** (D-14) replaces 2–4 above with a single 14px `--fg-2` line:
   *"Not enough data to project yet — {n} of {threshold} covered days."* The card shell (outlined,
   dashed `--provisional-border`) stays identical whether populated or degraded — only the inner
   content changes, so a viewer always recognises "this is the projection card" even when it has
   nothing to show yet.
6. **Card shell** — `border-dashed`, tinted `--provisional-border`, background `--provisional-bg`
   (one step quieter than the actual card's `--bg-1`/`--card` white) — the one new piece of visual
   grammar this phase introduces, and it is a **tint of an existing idiom**, not a new one (see
   Design Aesthetic).

**Absent, never zeroed (D-12, binding):** for any period that is not the current month or current
year (a past month, a past year, all-time), the entire "Projected" card is **not rendered** — the
KPI area collapses to a single "Revenue to date" card at its normal width, never a stretched
double-width card and never an empty dashed placeholder standing in for "no projection here."
Zeroing or greying-out a live card slot would itself read as a (wrong) forecast of nothing.

**Chart (binding):** the dashed forward segment on `RevenueChart` renders **only** when the
active period is the current month or current year (same D-12 gate as the KPI card); for every
other scope the chart is visually identical to today — one solid Cypher-Blue line, no dashed
segment, no legend entry for a series that does not exist for that scope.

## Color

Unchanged palette from every prior phase (60/30/10, Cypher Blue lead, brand semantic tokens).
Phase 7 adds exactly **one new semantic token group** — the "provisional/projected" surface
07-CONTEXT.md's D-17 explicitly flags as missing (confirmed absent this session by reading
`design-system/colors_and_type.css` in full). It is deliberately **not** a new hue: a forecast is
not an alarm, so it does not compete with `--success`/`--warning`/`--error` for the reader's
attention — it aliases existing, already-approved neutral tokens under names that make the intent
explicit in code, exactly as the existing semantic-status triads alias palette values.

**New tokens (add to both `design-system/colors_and_type.css`'s `:root` block and
`app/globals.css`'s `@theme` block, alongside the existing `--success`/`--warning`/`--error`
triads):**

```css
/* --- Semantic: provisional / projected (Phase 7) --------------- */
/* A forecast is not an alarm — this deliberately aliases existing
   neutral-ink tokens rather than introducing a new hue, so a projected
   figure reads as "not yet real" without competing with success/warning/
   error for attention. */
--provisional:        var(--cypher-ink-70);  /* muted figure/stroke ink — same value as --fg-2, contrast-checked at ~7:1 on white (AA-safe for bold 20px+ text) */
--provisional-border:  var(--cypher-ink-30); /* dashed card border — same value as --rule */
--provisional-bg:      var(--cypher-ink-04); /* quiet card background wash — same value as --bg-2 */
```

**Binding: never use `--cypher-ink-50` (`--fg-3`) for the projected point figure itself** — at
20px bold that tone fails WCAG AA for text (~2.6:1 on white); `--fg-3` remains correctly reserved
for captions, which are smaller/lighter by design and were already contrast-checked in that role.

| Role | Token | Usage (Phase 7, binding) |
|------|-------|----------------------------|
| Projected point figure, dashed chart line stroke, home sub-line | `--provisional` | The one recurring "this is inferred, not booked" ink — never `--cypher-blue` (that would read as equally real as the actual figure) and never `--warning`/`--error` (a forecast is not a problem) |
| Projected card border/background | `--provisional-border` / `--provisional-bg` | Reuses the existing dashed-border idiom (`EmptyState`/`PeriodEmptyState`), tinted to distinguish "not yet real" from "genuinely empty" |
| TSYS secondary figure (inside the actual card) | `--fg-2` | Neutral, de-emphasised ink — never colourised by source, consistent with `/alignment`'s existing rule that colour lives only in the status badge |
| Delta / which-side-short phrase (money) | `--fg-2` | Unchanged rule from Phase 4/6 |
| Band sentence, permanent method caption | `--fg-2` / `--fg-3` respectively | Band sentence is the substantive content (readable body ink); the caption is explanatory chrome (quietest ink) |
| Alignment Revenue card | Reuses `--success`/`--warning`/`--destructive` **exactly as the volume card's status determines** (D-11) | **Binding:** no independent colour computation for this card — its badge colour is a direct copy of the volume card's resolved status for the same period, never re-derived from the revenue figures themselves |

## Interaction & State Contract (trust-critical)

Every new surface keeps the **same 4-state contract as every prior phase** — loading / empty /
populated / error — plus the period-empty and period-absent (D-12) values introduced below. No
exceptions.

**Actual/projected KPI pair — binding rules:**
- The "Revenue to date" card's Bit Addict headline is drillable exactly as today (the existing
  `verification` drill entity, unchanged). **The TSYS secondary figure is explicitly NOT
  drillable this phase** — TSYS revenue rows come from `apigee_calls`, a different table with no
  existing drill entity, and adding one is out of scope here (07-CONTEXT.md left this
  undiscussed; recorded as a planner-visible gap below, not silently dropped).
- **The projected card is explicitly NOT drillable.** A projection has no "contributing rows" to
  drill into — some of the days it rests on have not happened yet, and clicking through to an
  empty or misleading row list would be worse than no affordance at all. (This resolves
  07-CONTEXT.md's open "whether the projected figure is drillable" item — declined; already
  logged in 07-CONTEXT.md's Deferred Ideas as the fallback if declined.)
- **D-12 gate:** the projected card and the chart's dashed segment render **only** when
  `period.of === currentUtcMonthOf(now)` (month scope) or the equivalent current-year check —
  **never** inferred merely from `resolvePeriod` returning successfully, since it also succeeds
  for every valid past month/year (07-RESEARCH.md Pitfall 5). A past period must render the
  single-card layout described above, not a projected card silently showing stale numbers.
- **D-14 gate:** below the configured covered-day threshold, the projected card renders its
  degraded message in place of the figure/band/caption — the card shell itself (dashed border,
  `--provisional-bg`) is unchanged between the populated and degraded states, so a viewer always
  recognises which card this is.
- **The method caption and band sentence are permanent and inline, never a tooltip** — same
  binding rule 06-UI-SPEC.md established for the live-cards derivation caption (D-08 precedent):
  these numbers reach leadership as screenshots, and a number this easy to misread must not hide
  its basis behind hover.
- Loading: both KPI cards render independent `skeleton` placeholders — a slow projection query
  never blocks the actual-to-date figure from appearing, and vice versa.
- Error: a failure computing the projection renders a card-scoped error (`{n/a}` figure,
  "Projected month-end could not be loaded.") that does **not** blank the "Revenue to date" card
  beside it — same per-card isolation principle as `PairedMetricCardError`.

**Chart — binding rule:** the dashed forward segment shares the D-12 gate above exactly — it
never renders for a past-period selection, and it never renders when the current period's
projection is in its degraded (too-few-covered-days) state (there is nothing honest to draw
forward from yet).

**`/alignment` Revenue card (fifth `PairedMetricCard` instance) — binding rules:**
- **Status is copied verbatim from the Transaction volume card's resolved status for the same
  period (D-11)** — never recomputed from the revenue figures themselves, and never given its own
  tolerance setting. The status-meaning caption (Copywriting) is **always rendered on this card
  specifically**, mirroring the live-cards precedent that a badge answering a different question
  than usual must say so on its face, not merely in documentation.
- `PairedMetricCard` gains a **currency formatting mode** for this instance (existing
  `formatCount` is a plain `.toLocaleString()`; the Revenue card needs `Intl.NumberFormat`
  currency formatting for both figures and for the delta phrase's absolute-difference term) — an
  extension of the existing component's formatting, not a new one-off card.
- The coverage statement on this card is **identical in wording** to the volume card's for the
  same period (same underlying coverage span) — reinforcing visually that the revenue verdict
  rides on the volume verdict, never an independently-stated coverage fact.
- The card's "day by day" affordance opens the **existing** `alignment-volume` drill (Copywriting:
  "Volume day by day →") rather than a new `alignment-revenue` entity — there is no
  revenue-specific per-day breakdown table; the volume breakdown is what actually explains any
  revenue difference, per D-11's own reasoning. No addition to `DRILL_ENTITIES` is needed for this
  card.
- Grid reflow: five cards in `grid-cols-1 sm:grid-cols-2` resolves to a lone card on the final row
  at `sm` and above — acceptable and expected (matches how the existing grid already behaves for
  any odd card count), not a defect to fix by forcing a three-column layout.

**Home revenue tile — binding rule:** the sub-line is present only when the home page's active
period is the current month/year **and** the projection clears the covered-day threshold; when
either condition fails, the tile renders exactly as it does today (headline figure + "View
revenue →" link, no sub-line, no degraded-state message) — the canonical explanation for "why no
projection" lives only on `/revenue` (unchanged from D-18's "home stays a one-glance summary,
canonical detail is one click away" framing).

**`/settings/general` contract (extension):**
- Three stacked sections, each in the existing bordered-block shape ("Dual-source alignment"'s
  own `rounded-lg border p-6` shell): **FY start**, **Dual-source alignment**, **Revenue
  forecast** (new, appended last) — a `Separator` between each, resolving the crowding concern
  07-CONTEXT.md flagged (D-15's "accepted consequence") by extending the same repeatable
  section pattern rather than introducing tabs, an accordion, or any new navigational structure.
  This keeps every setting reachable via one scroll, in a shape the page already uses twice.
- Field-level validation (positive integer ≥ 1) shows inline errors before submit where possible;
  a rejected submit shows the same banner-error pattern as the other two forms.
- The always-visible inline scope-impact notice wraps to multiple lines rather than truncating.

Focus rings (brand `--focus-ring`) visible on all new interactive elements (the new settings
input, the home tile's unchanged link) — unchanged rule from every prior phase.

## UI Considerations

State-coverage axis, produced by the post-research UI-consideration probe (2026-09-15). This
phase is executed autonomously (no live user session for the probe); every consideration below is
resolved directly from 07-CONTEXT.md's own binding decisions (D-01…D-19) or from an explicit,
justified researcher decision marked **[researcher decision]** — none are silently dropped, and
none are left as an unstated assumption. Shape-rooted STATE coverage only — empty/error-state
COPY lives in `## Copywriting Contract` above and is referenced rather than restated.

### E1 — `/revenue` actual/projected KPI pair

- Loading renders independent `skeleton` shapes for "Revenue to date" and "Projected
  month-end/year-end" — a slow forecast query never blocks the actual figure (see Interaction
  contract).
- Empty (no verification data at all) is unchanged from today — the existing page-level
  `EmptyState` still gates before either KPI card renders.
- Period-empty (activity exists elsewhere, none in the selected period) is unchanged — the
  existing `PeriodEmptyState` still gates before either card, per D-12's period gate applying
  before the projected card is even considered.
- Error on the projected card only renders a card-scoped failure, leaving "Revenue to date"
  readable (Interaction contract) — a projection failure must never blank an actual, already-known
  figure.
- Populated is the two-card layout described in Visual Hierarchy, with the TSYS secondary block
  nested inside the actual card (Design Aesthetic point 2).
- Partial: the actual card can be populated while the projected card is degraded (D-14, too few
  covered days) — this is the expected first-week-of-month case, not a partial-failure case; the
  degraded message (Copywriting) renders in the projected card's normal slot.
- Overflow: the band sentence and method caption wrap onto multiple lines within the card rather
  than truncating — both are short by construction (a handful of numbers and words) but neither is
  given a fixed-height container that could clip a wrap.
- Zero/one/many: not applicable to a fixed two-card (or one-card, D-12-absent) KPI pair — the card
  count is bound by scope, never by a data count.
- Long text: the largest realistic figure here is the TSYS MSA's own 25,000,000+/month tier
  ceiling priced through the ladder — a large currency figure at 14px (TSYS) or 20px (projected)
  renders in full with comma/decimal grouping; neither figure is ever abbreviated (`k`/`M`), per
  the app-wide no-abbreviation convention 06-UI-SPEC.md already documented.

### E2 — `RevenueChart` dashed forward segment

- Loading is unchanged — the existing chart `skeleton` covers both series together (there is one
  fetch, not two).
- Populated (current month/year, threshold cleared) shows the solid actual line meeting a dashed
  `--provisional` line at today's data point, per the two-`dataKey`/`connectNulls={false}` pattern
  in 07-RESEARCH.md's Pattern 3.
- Populated (any other scope, or degraded threshold) shows only the solid line — no dashed
  segment, no empty legend entry for a series that has nothing to plot (D-12/D-14 gate, shared
  with the KPI card).
- Overflow: the chart's existing responsive container and axis behaviour are unchanged; the
  dashed segment adds no new horizontal-scroll risk since it occupies the same date axis as the
  actual series, only extending it to month/year-end.

### E3 — `/alignment` Revenue card (fifth `PairedMetricCard`)

- Loading/empty/error/populated are unchanged from the existing four cards' documented states in
  06-UI-SPEC.md §E2 — this is a fifth instance of the same component, not a new shape.
- Partial: the D-12 incomplete-coverage rule (forces `needs_review`) still applies, inherited from
  the volume card's status (D-11) rather than independently recomputed here.
- The zero-denominator em-dash percentage handling (06-UI-SPEC.md's D-14 pattern) applies
  identically when Bit Addict's revenue figure is exactly zero for the period.
- Grid reflow at five cards resolves to a lone trailing card at `sm`+ — expected, not a defect
  (Interaction contract).

### E4 — Home revenue tile sub-line

- Loading renders the sub-line's own `skeleton` line beneath the existing tile skeleton,
  independent of the other two home tiles.
- Absent (projection not computable, or scope is not current month/year) — the tile renders
  exactly as it does today; this is the common case in the first week of any month and must never
  read as a missing/broken tile.
- Populated sub-line sits directly beneath the 48px headline value, above the "View revenue →"
  link — a long formatted sub-line value (currency with comma grouping) wraps rather than
  truncating, matching 06-UI-SPEC.md's E6 rule for the headline value itself.
- Error: a sub-line-specific failure (projection query fails, headline figure succeeds) degrades
  to the absent case (no sub-line) rather than surfacing a second error message on an already
  information-dense tile — the canonical error lives on `/revenue`.

### E5 — `/settings/general` "Revenue forecast" section

- The new field renders with its current persisted value on load (populated state); a pending
  save disables the save button and shows its submitting state, matching the other two sections.
- An unset threshold renders its documented default (7) rather than an empty input, so the
  effective value is never ambiguous.
- A rejected submit shows the same banner-error pattern as the other two forms; field-level
  validation (`Enter a whole number of 1 or more.`) shows inline before submit where possible.
- The always-visible inline scope-impact notice wraps to multiple lines rather than truncating.
- **[researcher decision]** The three settings sections stack vertically with a `Separator`
  between each, rather than a tabbed or accordion layout — resolves D-15's flagged crowding concern
  by extending the page's own existing repeatable pattern (see Interaction contract) rather than
  introducing new navigational chrome for a page with only three groups of two fields each.
