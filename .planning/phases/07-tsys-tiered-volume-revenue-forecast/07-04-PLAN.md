<objective>
Build the projection in SQL: extract the proven marginal-bracket formula into a reusable pricing
function, add a tier-set resolver that works for a day with no activity yet, and build a
period-scoped forecast RPC that projects volume at the covered-day run rate and prices that volume
through the ladder — per month, then summed — for the point figure and for both band bounds
independently. Lock the two ways this can go wrong with a strictly read-only regression oracle.

Purpose: ROADMAP SC3 (FCST-03) and SC5 (FCST-05). D-06 names the linearly-scaled priced figure as
this phase's single most natural-looking mistake; L-02 names the aggregate-ladder path as the
other. Both are locked by assertion here rather than by review.

Output: migrations `0036_price_volume_through_tier_set.sql` and `0037_revenue_forecast.sql`, plus
`supabase/tests/revenue_forecast_test.sql`.

<planner_notes>
**One code path for both horizons (planner decision, Claude's Discretion per 07-CONTEXT).** The
month horizon and the year horizon are the SAME algorithm: iterate the calendar months intersecting
the period, project each month's volume at the applicable rate, price each month independently
through its own governing tier ladder, then sum the priced figures. A one-month period is simply the
degenerate case. This structurally enforces L-02 — there is no code path that could run the ladder
over a multi-month aggregate — and removes the need for a scope parameter. D-13's "the year uses
the year-to-date rate" falls out for free: the rate is computed once over the whole period span, so
a month period yields the month-to-date rate and a year period yields the year-to-date rate, and
the caller labels which one it displayed.

**The inference window is floored at the data window (planner decision).** Uncovered days are filled
at the run rate per D-03, but that rule is about days we have not received, not about days before
the system existed. Every view in this codebase carries the `2026-08-13` cutoff; the forecast does
too, as `inference_start = greatest(p_start, date '2026-08-13')`. Without this floor a current-year
projection would invent revenue for January through July 2026. This does not contradict D-03 — a
pre-window day is out of scope, not uncovered.

**The band bounds use the same usable-day set as the run rate (planner decision).** "Our quietest /
busiest day so far" (D-05) is measured over the usable days, i.e. covered days excluding the most
recent one, because the trailing day is routinely partial (D-02) and would otherwise almost always
be the minimum. A covered day on which the source reported nothing counts as a genuine zero and is
included.

**Tier-set resolution is NEW logic, not a reuse (RESEARCH Pitfall 4).** `v_revenue_tier_set_by_day`
is built bottom-up from actual activity and has no row for a day with no volume yet, so it cannot
answer "which tier set governs the rest of this month". `pricing_tier_set_effective_on` queries
`pricing_tier_sets` directly. The migration header must say so explicitly, matching this codebase's
convention of stating what is and is not being reused.

**The monthly-reset assumption is guarded, not assumed.** `price_volume_through_tier_set` treats its
volume argument as a whole month's counter starting from zero, which is only valid when the
governing tier set resets monthly. The forecast therefore checks the resolved set's `reset_window`
and degrades with a reason rather than silently mispricing. The seeded TSYS MSA set is monthly
(`0026_tsys_msa_tier_seed.sql`), so this guard should never fire today — which is exactly why it
must be a guard and not a comment.

**The regression oracle is strictly read-only, and that is only possible because of the
extraction.** `tsys_msa_tier_test.sql` and `revenue_boundary_test.sql` prove their invariants by
deleting and re-inserting fixtures, which this project has previously run against production over
the MCP `execute_sql` path and destroyed real rows. Because `price_volume_through_tier_set` is a
pure function over the already-seeded live tier set, every SC3 and D-06 invariant can be asserted
with function calls alone — no fixture, no transaction, no writes. Do not reintroduce a fixture
here.
</planner_notes>

**What is being decided:** the physical shape of the forecast computation. 07-CONTEXT.md leaves
this to Claude's discretion, subject to the binding D-05/D-06 constraints. The proposed shape is
below; it is presented for confirmation before any SQL is written, because it is the one decision
in this phase that cannot be cheaply reversed after the figures reach a screenshot.

**Proposed shape**

1. Extract the marginal-bracket overlap formula already proven correct in `v_revenue_by_tier` into
   a pure function `price_volume_through_tier_set(tier_set_id, volume)`. Every projected figure —
   point, low band, high band, and every per-month component of a year projection — is produced by
   calling this one function. There is no second pricing implementation anywhere.
2. Project **volume**, never money. The run rate is a volume-per-day figure; the projected volume
   is `actual_volume + rate x uncovered_days`; only then is it priced. A priced figure is never
   multiplied by a day ratio.
3. Compute the low and high bounds as two further independent volumes (remaining days at the
   quietest covered day's volume, and at the busiest covered day's volume) and price each through
   the ladder separately. Neither bound is derived from the point figure.
4. Treat the month horizon and the year horizon as one algorithm: iterate the calendar months the
   period covers, project and price each month independently, then sum. A year figure is therefore
   structurally the sum of per-month tiered figures (L-02) rather than by convention.
5. Take no wall-clock reading inside SQL. Period bounds are parameters; "the latest day we have
   data for" comes from the coverage views.
6. Degrade rather than guess: below the configured usable-day threshold, or when the governing
   tier set does not reset monthly, return a degradation reason and no figure.

**Alternatives considered and rejected**

- Scaling the actual priced revenue by `days_in_month / covered_days`. Rejected: D-06 forbids it
  outright, and under stepped tiers it prices the projected units at the already-reached tier's
  blended rate rather than at the marginal brackets they actually fall into.
- Deriving the band as a percentage either side of the point figure. Rejected: D-05, and
  RESEARCH Pitfall 3 — it reintroduces the same linear-scaling error one level up.
- Re-deriving the overlap formula inline in a new forecast view rather than extracting it.
  Rejected: two hand-written copies of the same money-critical formula is the "two money code
  paths that can drift" risk D-07's own reasoning names.
- A separate year-specific function. Rejected: two implementations of "sum the per-month figures"
  is exactly how L-02 gets violated by drift.

**What to confirm:** that this is the shape to build, and in particular that the data-window floor
on the inference window (no projection invented for days before 13 Aug 2026) is correct.
  </decision>

`v_revenue_by_tier` into a pure function so that the point projection and both band bounds call the
same proven code rather than a second hand-written copy; that `pricing_tier_set_effective_on` is
NEW logic with no existing analog, deliberately querying `pricing_tier_sets` directly because
`v_revenue_tier_set_by_day` is activity-driven and has no row for a day with no volume yet

when no set governs that day. Add a `comment on function` and the revoke/grant triplet.

Create `price_volume_through_tier_set(p_tier_set_id uuid, p_volume numeric) returns numeric`,
`language sql`, `stable`, `security invoker`, `set search_path = public`. Body: sum, over every
`pricing_tiers` row in the set, `greatest(0, least(p_volume, coalesce(pt.upper_bound::numeric,
'infinity'::numeric)) - greatest(0, coalesce(lb.lower_bound, 0))) * pt.rate`, where `lb` is a

`(tier_set_id, tier_order - 1)` — a correlated subquery on those two columns only, never a window
function. Wrap the sum in `coalesce(..., 0)` so an unknown tier set returns zero rather than null.
Every operand is exact NUMERIC; no approximate binary numeric type appears anywhere in the body.
Add a `comment on function` naming the formula's origin and the monthly-reset assumption, then the
revoke/grant triplet.

**Migration `0037_revenue_forecast.sql`.**

Header comment: state the algorithm in full (it has no analog in this codebase and a future reader
must be able to check it without reconstructing it); name D-01, D-02, D-03, D-05, D-06, D-12,
D-13, D-14 against the lines that implement them; state that the month horizon and the year horizon
are one algorithm and why that structurally enforces L-02; and state the data-window floor on the
inference window.

Create `revenue_forecast_for_period(p_start date, p_end date, p_source text,
p_min_covered_days int)` as a `returns table (...)` function, `language sql` or `plpgsql` as the
body requires, `stable`, `security invoker`, `set search_path = public`. `p_end` is required — a
projection needs a bounded horizon, and the caller never asks for one on an open-ended scope.

Returned columns: `as_of_day date`, `covered_days int`, `usable_days int`, `inferred_days int`,
`run_rate numeric`, `min_day_volume numeric`, `max_day_volume numeric`, `actual_volume numeric`,
`projected_volume numeric`, `low_volume numeric`, `high_volume numeric`,
`projected_revenue numeric`, `low_revenue numeric`, `high_revenue numeric`, `degraded boolean`,
`degraded_reason text`.

Computation, all in exact NUMERIC:

- `inference_start` is the later of `p_start` and the date literal `2026-08-13`.
- The per-day volume series for the requested source is `v_revenue_daily_counts` restricted to
  `source = p_source`, its `day_utc` cast to `date`, over `[inference_start, p_end)`.
- The coverage day set is `v_apigee_coverage_daily` when `p_source` names the TSYS side and
  `v_verification_coverage_daily` when it names the Bit Addict side, restricted to the same range.
  Resolve which one by a case expression on `p_source`; do not build a second coverage view.
- `covered_days` is the number of days in the coverage set. `as_of_day` is the maximum day in it —
  the dataset's own maximum, never a wall-clock reading.
- `usable_days` is `covered_days - 1` floored at zero (D-02: the most recent covered day is
  dropped from the rate, though its volume still counts in `actual_volume`).
- `actual_volume` is the sum of the per-day volume series over the whole range, including the
  dropped day.
- `run_rate` is the sum of volume over the usable days divided by `usable_days`, or null when
  `usable_days` is zero. `min_day_volume` and `max_day_volume` are the minimum and maximum per-day
  volume over those same usable days, where a covered day with no volume row counts as zero.
- `inferred_days` is the number of days in `[inference_start, p_end)` minus `covered_days` (D-03).
- `degraded_reason` is set, in this precedence order, to a marker meaning no governing tier set,
  then a marker meaning the governing set does not reset monthly, then a marker meaning too few
  usable days when `usable_days < p_min_covered_days`; otherwise null. `degraded` is true exactly
  when `degraded_reason` is non-null. When degraded, every projected volume and revenue column is
  null — never zero.
- The three projections: for each of the three rates (`run_rate`, `min_day_volume`,
  `max_day_volume`), iterate the calendar months intersecting `[inference_start, p_end)`. For each
  month, clip the month to the range to get that month's start, exclusive end and day count; count
  that month's covered days; sum that month's actual volume; compute
  `month_volume = month_actual + rate * (month_days - month_covered)`; resolve the governing tier
  set with `pricing_tier_set_effective_on` applied to the month's last in-range day; and price
  `month_volume` with `price_volume_through_tier_set`. Sum the priced per-month figures to get that
  rate's revenue column, and sum the per-month volumes to get its volume column. Run the three
  rates through three separate passes — the low and high revenue figures must each be priced from
  their own volume, never derived from `projected_revenue`.
- The function body must contain no wall-clock call of any kind. Every date is a parameter or is
  derived from the coverage views.

Create `revenue_forecast_daily_for_period(p_start date, p_end date, p_source text,
p_min_covered_days int)` returning `table (day date, revenue numeric, is_projected boolean)`, same
function attributes and grants. It returns zero rows when the equivalent
`revenue_forecast_for_period` call is degraded. Otherwise, for each day in
`[inference_start, p_end)`: the day's volume is its actual volume when the day is covered (zero if
covered with no rows), and `run_rate` when it is not covered; the running cumulative volume is
summed within that day's own calendar month, resetting at each month boundary; the day's revenue is
`price_volume_through_tier_set` of the cumulative volume through that day minus the same function
of the cumulative volume through the previous day in the same month (zero at a month's first day) —
which is volume-then-price at day granularity and never a scaled priced figure; `is_projected` is
true when the day is after `as_of_day` or is not covered. Order by day.

Add `comment on function` for both, then the revoke/grant triplet for each: revoke execute from
`public`, revoke execute from `anon`, grant execute to `authenticated`.
