<objective>
Thread a `source` dimension (`'tsys'` | `'bit_addict'`) through the existing `0012_v_revenue.sql`
marginal-bracket chain so revenue is computed independently per source through one ladder
implementation, and make every existing consumer source-explicit in the same change so nothing
silently starts double-counting. This is the phase's tracer: one path from `apigee_calls` /
`verifications` through the full view chain, through the period-total RPC, into `/revenue`'s KPI
card, with the TSYS figure rendered beside the Bit Addict headline.

Purpose: ROADMAP SC2 (FCST-02) — a TSYS-vs-Bit-Addict volume disagreement must be visible as a
revenue disagreement. Everything later in this phase (the forecast, the alignment revenue card,
the home sub-line) is priced off this chain.

Output: migration `0034_v_revenue_source.sql`, a read-only live invariants oracle, a per-source
fetcher module, and a `/revenue` "Revenue to date" card that shows Bit Addict as the headline with
TSYS beside it.

**User story (surfaced, not invented):** `.planning/ROADMAP.md` §"Phase 7" records the phase goal
as *"Turn billable transaction volume into money the way the MSA actually pays it — TSYS stepped
tiers on monthly volume — and show actual-to-date alongside a projected month-end forecast, for
both sources, for any selected period."* MVP_MODE is enabled but this Goal line is **not** in
`As a / I want to / so that` form. Per the MVP-mode contract no story has been invented here; run
`/gsd mvp-phase 7` if a formal user story is wanted before execution.
</objective>

<assumption_delta_decision>
The `assumption-delta` probe fired (`kind: pluralization`) on this phase's scope: one revenue
figure becomes two attributable ones.

- **Noun that is now primary:** `(day, source)` revenue — not `day` revenue. A daily revenue row is
  now identified by the day *and* the source that produced it.
- **Decision: `promote`.** The source-dimensioned chain becomes the only chain. The old
  single-source shape is demoted to "the `source = 'bit_addict'` slice of it", and every consumer
  that previously relied on the implicit single source now names it. The two-argument
  `revenue_total_for_period(date, date)` is dropped rather than kept alongside the three-argument
  form, so no caller can keep reading the pre-dimension shape.
- **Why not `add-alongside`:** keeping the old two-argument function or a parallel
  `v_revenue_tsys_*` chain would leave two money code paths that can drift, which is exactly what
  D-07 forbids, and would let a stale call site keep compiling while returning a doubled figure.
- **Invariant encoded:** `supabase/tests/revenue_source_invariants_test.sql` asserts that the only
  `source` values in the chain are `tsys` and `bit_addict`, and that the Bit Addict slice alone
  reproduces the pre-refactor whole-chain total.
</assumption_delta_decision>

**Call-site inventory is larger than 07-RESEARCH.md reported.** RESEARCH grepped `app/` and `lib/`
and found four sites. This planning run also grepped `supabase/migrations/` and found **two
further SQL consumers that RESEARCH missed**, both of which would silently double-count:

1. `v_revenue_total` (`0017_v_revenue_total.sql`) — `sum(revenue) from v_revenue_daily`.
2. `v_reconciliation_billing_daily` (current definition in `0022_reconciliation_no_source_data.sql`
   lines 142–212) — `full outer join v_revenue_daily_counts v using (day_utc)` **and**
   `(select max(day_utc) from v_revenue_daily_counts) as max_verification_day`.

The second is the serious one: it is the core-value billing-vs-verification reconciliation, and an
unfiltered join against a two-rows-per-day view would double the verification side of every
reconciliation row. Both are fixed in this plan's migration.

**No `drop ... cascade` anywhere.** Postgres allows `create or replace view` to append new columns
at the END of the column list without dropping dependents. Every view in the chain therefore keeps
its existing column names, types and order and gains `source` as the final column — which is what
makes it possible to replace `v_revenue_daily_counts` without cascading away
`v_reconciliation_billing_daily`. Adding `source` anywhere but last, or using `drop view ...
cascade`, will fail or destroy the reconciliation chain.

**`npx tsc --noEmit` cannot catch a stale RPC call site in this repo.** `lib/supabase/server.ts`'s
client is not parameterised with the generated `Database` type (stated verbatim in
`lib/dashboard/alignment.ts`'s own comment), so `supabase.rpc(...)` arguments are untyped.
07-RESEARCH.md Pitfall 2's "TypeScript will surface the new required parameter" mitigation does NOT
hold here. The loud-failure mechanism is instead (a) dropping the two-argument overload so a stale
call errors at runtime with PostgREST `PGRST202`, and (b) the structural grep gates in this plan's
acceptance criteria.

**`countRestatedDays` semantics (07-RESEARCH.md Open Question 1 / Assumption A2, resolved here).**
It becomes a genuine distinct-day count across both sources: a day on which either source recorded
activity is a day whose priced figure a tier-set edit can restate. It is a UI warning count, not a
money figure, so deduplicating day strings in TypeScript is allowed (L-01 binds money arithmetic
only).
</planner_notes>
