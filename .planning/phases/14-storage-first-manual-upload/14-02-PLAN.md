<objective>
Remove the three measured memory failures that stand between this project and a 100 MB file:
the header read that parses a whole CSV inside the synchronous claim, the unbounded ExcelJS load,
and whole-file billing processing in the background function.

Purpose: D-06 (processing, not just transfer, must survive month-end size), D-16 (XLSX capped at
15 MiB), D-03 (billing goes through, at any size up to the ceiling). Research measured all three
through the real code path; this plan fixes each where it lives and proves equivalence by test,
without touching a single fenced parser, handler or normaliser.

Output: a sliced header read, an XLSX cap inside claimFile, a windowed billing branch, and two
scripts that let anyone re-take the numbers.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| uploaded bytes to the claim function | attacker-shaped CSV/XLSX content parsed inside a 1024 MB function |
| uploaded bytes to the background function | the same bytes, fully parsed and written to revenue tables |
| local scripts to the deployed site | synthetic files leave the executor's machine for the deployed proof |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-08 | Denial of service | extractHeaderSignature full parse | high | mitigate | decode and parse at most HEADER_SLICE_BYTES with preview 1; spy test bounds every Papa.parse input to 65,536 characters |
| T-14-09 | Denial of service | ExcelJS load of a large workbook (poison pill for claim and drain) | high | mitigate | MAX_XLSX_BYTES guard inside claimFile before any ExcelJS import; recorded as a kept, failed row, so the object is terminal and never retried into an OOM |
