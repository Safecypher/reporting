    - Total function: with every dep throwing, and with an onStage callback that throws, uploadViaStorage still resolves to an outcome and never rejects.
  </behavior>
  <action>
    Create lib/upload/transfer.ts (pure; no browser globals, no Supabase import; types only from
    lib/ingestion/types and lib/upload/batch) exporting:
    - type MintResult = { ok: true; path: string; token: string } | { ok: false; status: number }
    - type ClaimResponse = { status: number; body: unknown }
    - interface TransferDeps { fileName: string; mint(): Promise<MintResult>; put(path: string, token: string): Promise<boolean>; claim(path: string): Promise<ClaimResponse>; onStage?(stage: "uploading" | "checking"): void }
    - async function uploadViaStorage(deps: TransferDeps): Promise<BatchFileOutcome>
    Algorithm: up to two attempts. Each attempt signals onStage("uploading") (wrapped so a throwing
    callback is ignored), mints (a throw or non-ok status maps as in the behaviour list), then puts
    (a throw counts as false). A failed put on attempt 1 starts attempt 2 with a NEW mint; on attempt
    2 it returns UPLOAD_INTERRUPTED_MESSAGE. After a successful put, signal onStage("checking") and
    claim exactly once (no claim retry: a claim failure is already safe under D-15), then map the
    response: 200 with an object body is a result; 202 with body.status "pending" and a string fileId
    is pending (carry reportType); 413 is failed with FILE_TOO_LARGE_MESSAGE; everything else,
    including a thrown claim, is received with RECEIVED_MESSAGE. The whole body sits in a try/catch
    that returns failed with UPLOAD_FAILED_MESSAGE, so the function is total by construction. Header
    comment: this function is the putToStorage seam research names, so a TUS transfer could replace
    deps.put without touching the dropzone loop (D-07 contingency).

    Write lib/upload/__tests__/transfer.test.ts first with vi.fn deps covering every behaviour above.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client bundle to server code | anything imported by a client component ships to every browser |
| browser to Storage | the signed PUT runs with the publishable key and the minted token |
| server responses to the screen | claim/mint bodies are rendered as user-visible copy |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-17 | Information disclosure | secret key reaching the client bundle | high | mitigate | dropzone uses createClient from lib/supabase/client (publishable key) only; a grep gate over every touched client file forbids the secret-key client and the server writer; npm run build must succeed |
| T-14-18 | Information disclosure | server error detail rendered to users | low | mitigate | every status maps to curated constants in lib/upload/batch.ts; response bodies are never rendered as text (T-ILI-02 rule kept) |
| T-14-19 | Repudiation / Integrity | a held file reported as failed, prompting duplicate re-uploads | medium | mitigate | after a successful transfer every claim failure maps to received (D-15), pinned by transfer.test.ts |
| T-14-20 | Tampering | the retry creating a second object for the same bytes | low | accept | the retry uses a fresh key; an orphan from a first attempt that actually landed is drained later and collapses by content hash (findFileByHash / UNIQUE content_sha256) |
| T-14-SC | Tampering | npm installs | high | mitigate | nothing installed; TUS (tus-js-client) stays a contingency behind its own legitimacy checkpoint, not used here |
</threat_model>
