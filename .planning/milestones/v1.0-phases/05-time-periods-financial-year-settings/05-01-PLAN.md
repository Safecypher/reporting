<objective>
Prove the whole Phase 5 period architecture end to end on one view. Land the `app_settings`
store that holds the financial-year start (D-10/D-11/D-12/D-13), the pure `lib/dashboard/period.ts`
resolver that turns `{period, of, yearMode}` plus that setting into a `[start, end)` UTC range
(D-01/D-05), and wire exactly one metric view — `/verifications` — through it: URL param ->
whitelist parse -> resolved range -> outer `.gte`/`.lt` predicate on the unchanged
`v_verifications_daily` view -> an active-scope badge stating the period actually applied.
Then add the user-facing control cluster and the period-empty state so a real user can change
period by clicking, not just by editing the URL.

Purpose: this is the tracer. Every remaining view in Phase 5 is a replication of what this plan
proves. Getting the layer split right here — pure resolver in TS, filtering in Postgres via an
outer predicate that never touches an existing view's internals — is what structurally guarantees
D-06 (period scoping never changes the tier maths) for the whole phase.
Output: migration 0023, a tested pure period module, a server-side FY reader, three new dashboard
components, the shadcn `select` primitive, and a fully period-scoped `/verifications`.
</objective>

<assumption_delta_decision>
**Noun now primary:** *a resolved period window*.

Before this phase every metric view had no window at all — "all time" was the absence of a
predicate, not a chosen scope, and the financial-year boundary did not exist as a value anywhere.
The generalised identity that replaces both is a single `ResolvedPeriod` produced by one resolver.

**Decision: `promote`.** The resolved period becomes the primary path every metric view takes;
there is no un-scoped variant left alongside it. `all` is one scope value the same resolver
returns (`start = 2026-08-13`, `end = null`), not a bypass. Promoting rather than adding
alongside is what makes ROADMAP SC2 ("every metric view accepts the same period scope") checkable
by construction instead of by inspection, and it is what D-03 already commits to — the current-month
default is a deliberate break, and leaving an unscoped default path in place would quietly restore
the old behaviour on whichever view forgot to opt in.

**Suggested invariant (not required):** a gate asserting that every one of the five metric page
files imports from `lib/dashboard/period` and applies the resolved range — encoded as an
`<automated>` check in plan 05-05, so "for every scope, every metric view resolves its window
through the same resolver" is enforced rather than assumed.
</assumption_delta_decision>

<planner_decisions>
Open questions the ROADMAP handed to planning, resolved here as explicit, recorded choices
rather than left to the implementer:

- **P-01 — Default `yearMode` is `calendar`.** When Year is first selected and no `yearMode`
  param is present, the resolver returns `calendar`. Rationale: `app_settings` ships with the FY
  start defaulting to 1 January, so a `financial` default would be numerically identical to
  calendar on first use while labelling the figures "FY" — implying a configured financial year
  that nobody has configured. Calendar is also the order the UI-SPEC copy table lists.
  Reversibility: reversible (one constant in `lib/dashboard/period.ts`).
- **P-05 — A financial year with a non-1st start day is a legitimate period, and D-07's
  rejection of free from/to ranges does not extend to it.** D-07 rejected an arbitrary partial-month
  range because it has no valid tiered figure under a monthly reset. An FY window such as
  6 Apr -> 5 Apr also cuts two months in half, so the tension must be stated: the FY figure is the
  **sum of already-computed per-day marginal amounts** for the days inside the window. Each day's
  amount was bracketed against its own month's running counter before any period predicate applied
  (D-06), so a part-month FY edge sums correct daily accruals — it never re-runs the ladder over a
  partial volume. That is exactly what an accrual-basis financial year means, and it is why an
  outer predicate is safe where a re-parameterised view would not be.
</planner_decisions>

New — `lib/dashboard/period.ts` (pure, no network/DOM, `today` injected):

```
export type PeriodScope = "month" | "year" | "all";
export type YearMode = "calendar" | "financial";
export interface FinancialYearStart { month: number; day: number }   // month 1-12, day 1-31

export interface ResolvedPeriod {
  scope: PeriodScope;
  yearMode: YearMode | null;   // null unless scope === "year"
  of: string | null;           // canonical "YYYY-MM" (month) / "YYYY" (year); null for "all"
  start: string;               // "YYYY-MM-DD", INCLUSIVE
  end: string | null;          // "YYYY-MM-DD", EXCLUSIVE; null means open-ended ("all")
  label: string;               // "August 2026" | "2026 (calendar year)" | "FY2026-27 (6 Apr 2026 - 5 Apr 2027)" | "all time"
}

export const DATA_WINDOW_START: string;                 // "2026-08-13"
export const DEFAULT_YEAR_MODE: YearMode;               // "calendar" (P-01)

export function resolvePeriod(
  params: Record<string, string | string[] | undefined>,
  fyStart: FinancialYearStart,
  today: Date,
): ResolvedPeriod;

export function resolveFinancialYearBounds(
  fyStart: FinancialYearStart,
  today: Date,
): { start: Date; end: Date; fyLabel: string };

export function monthOptions(today: Date): { value: string; label: string }[]; // reverse-chron
export function yearOptions(today: Date): { value: string; label: string }[];  // reverse-chron
export function serializePeriodParams(p: ResolvedPeriod): Record<string, string>;
```
