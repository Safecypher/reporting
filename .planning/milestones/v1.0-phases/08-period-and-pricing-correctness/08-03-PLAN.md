# 08-03 — The coverage guard: a lock and a committed test

## Objective

The data-window coverage guard in `0025_pricing_tier_edit_in_place.sql` is the thing standing
between an operator's tier-set edit and a database where some day in the reliable-data window
has no governing price. Round 3 hand-traced its semantics and found them sound. It has never had
a committed test, and it takes no lock.

No file here overlaps 08-02, so the two run in parallel.

---

## Task 1 — migration 0039: the lock, and the SQL side of WR-07

**New file:** `supabase/migrations/0039_pricing_tier_coverage_guard_lock.sql`. Next free number
— 0038 is the highest applied.

**Do not edit `0025`.** It is applied history. This migration is a forward-only
`create or replace` of `save_pricing_tier_set` and `delete_pricing_tier_set`, keeping their exact
existing signatures so no call site changes and `types/db.ts` needs no regeneration. This is the
pattern 0038 established for exactly this situation.

Three changes, and nothing else:

1. **Add `data_window_start()`** — an `immutable` SQL function returning `date '2026-08-13'`,
   `security invoker`, `set search_path = public`. This is WR-07's SQL half. Its scope is
   deliberately narrow: **it is used by this migration and by new SQL from here on. The 20+
   existing migrations that contain the literal are applied history and must not be rewritten.**
   Say so in a comment in the migration, so the next person does not read a half-adopted helper
   as an unfinished job.

2. **Replace the four hardcoded `date '2026-08-13'` occurrences** (0025 `:69`, `:163`, `:211`,
   `:229`) with `data_window_start()` in the two recreated functions.

3. **Take a lock before evaluating coverage.** Today both RPCs evaluate a bare
   `select exists(select 1 from pricing_tier_sets where effective_from <= …)`. Two concurrent
   transactions can each observe coverage surviving their own write and both commit, leaving the
   union uncovered. Serialise them.

   Prefer `pg_advisory_xact_lock` on a fixed key over `select … for update`. The guard's predicate
   is about the *set* of rows, not any particular row — a `for update` on the rows that happen to
   match today does not lock the absence of a row, and the delete path's hazard is precisely that
   the last covering row disappears. An advisory transaction lock, taken by both RPCs before
   either evaluates coverage, serialises the whole check-write-check sequence, which is what the
   invariant actually needs. Document the chosen key and the reasoning in the migration.

Preserve everything else exactly: `security definer` on both (unchanged from 0025 — the table
has no DELETE RLS policy and no client INSERT policy on the audit table, so an invoker call
would be denied), the before-and-after global predicate structure, the audit-row-before-delete
ordering that keeps `ON DELETE SET NULL` from blanking the summary text, and every error message
and SQLSTATE the UI's error mapper already matches on.

**Verify:**

## Task 2 — `supabase/tests/pricing_tier_coverage_guard_test.sql`

Mirror the house pattern. **Read `revenue_boundary_test.sql` and `tsys_msa_tier_test.sql` first
and follow whichever convention they establish** — do not invent a third style.

Note the split in the existing suite, and choose deliberately:
- `revenue_forecast_test.sql` and `revenue_source_invariants_test.sql` are strictly **read-only**
  (no `begin`/`rollback`, no writes) so they are safe to run through MCP, the SQL editor, or psql
  alike.
- This guard cannot be tested read-only. Proving it *rejects* a write requires attempting one.

So this test needs `begin; … rollback;` and must be explicit at the top of the file that it
writes inside a transaction it always rolls back, and that it must never be executed
statement-by-statement through a tool that would drop the transaction wrapper. There is a
recorded hazard here — `tsys_msa_tier` and `revenue_boundary` tests have previously deleted
production data when run via MCP `execute_sql` — so make the warning prominent and unmissable.

Cover at minimum:
1. A `save_pricing_tier_set` UPDATE that would move the only covering set's `effective_from`
   past the floor raises `check_violation`
2. The same write succeeds when another set still satisfies the floor
3. A `delete_pricing_tier_set` on the only covering set raises `check_violation`
4. The same delete succeeds when another covering set remains
5. The before-covered/after-uncovered transition rule: a database already uncovered *before* the
   operation is not locked by the guard (Phase 5 D-17/D-19 — this is deliberate, so a database
   in a bad state stays correctable)
6. `data_window_start()` returns exactly `2026-08-13`

Case 5 matters most. It is the subtlety that makes the guard correct rather than merely strict,
and it is the one a future refactor is most likely to break while keeping cases 1-4 green.

**Verify:**
```bash
# Transaction wrapper present and balanced — the opposite of the read-only oracles' rule
bash -c 'b=$(grep -c "^begin;" supabase/tests/pricing_tier_coverage_guard_test.sql); r=$(grep -c "^rollback;" supabase/tests/pricing_tier_coverage_guard_test.sql); [ "$b" -eq 1 ] && [ "$r" -eq 1 ] && echo "TXN_WRAPPER_OK" || echo "TXN_WRAPPER_BAD begin:$b rollback:$r"'
# The destructive-run warning is present
bash -c 'if grep -qi "rollback" supabase/tests/pricing_tier_coverage_guard_test.sql && grep -qiE "never|must not|do not" supabase/tests/pricing_tier_coverage_guard_test.sql; then echo "HAZARD_WARNING_PRESENT_OK"; else echo "HAZARD_WARNING_MISSING"; fi'
# Six assertions
bash -c 'n=$(grep -v "^--" supabase/tests/pricing_tier_coverage_guard_test.sql | grep -c "raise exception"); [ "$n" -ge 6 ] && echo "ASSERTIONS_OK:$n" || echo "ASSERTIONS_THIN:$n"'
```
