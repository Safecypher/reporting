<objective>
Close WR-08's consumer half. `resolveEditImpact` computes `futureSupersededBy` correctly and is
unit-tested, but nothing reads it: `grep -rn futureSupersededBy app components lib` returns only
the declaration, its computation, and its own tests. Two defects follow, and both are closed here.

1. **Missing disclosure.** The dialog interpolates only `supersedes`. The operator is never told
   about the further-out set that permanently absorbs the edited set's own former future territory
   — the exact fact WR-08 exists to require.

2. **A silent-bypass regression, the more serious half.** The submit gate keys on the single-limb
   condition over the resolved impact's crossed-neighbour field, and *that branch* carries the
   "ALWAYS open the confirmation, regardless of day count" guarantee (G-05-CR01). The far-future
   field can fire while the crossed-neighbour field is `null`, routing around the guarantee
   entirely. Confirmed reachable against the shipped resolver, two tier sets, no exotic fixture:

   - `y` effective `2026-08-01`; edited set `e` effective `2026-09-01`; operator backdates `e` to
     `2026-07-15`.
   - Executed against `lib/pricing/restate-scope.ts` during planning, actual returned value:
     `{ from: "2026-07-15", through: null, supersedes: null, futureSupersededBy: "2026-08-01" }`.
   - The form's supersede branch is therefore skipped, execution falls through to the day-count
     path, and **at zero affected days it saves immediately with no dialog at all** — a permanent,
     silent transfer of pricing authority to a set the operator was never shown.

The fix restates the gate's question as **"did pricing authority move"**, not "is the crossed-
neighbour field set". Governance is `v_revenue_tier_set_by_day`'s `order by effective_from desc
limit 1` — highest `effective_from` not exceeding the day wins, for every day, forever. Every date
claim below is derived from that rule.

Purpose: Roadmap Phase 8 Success Criterion 3 — an operator editing a tier set is told the whole
truth about which contract ends up pricing which days.
Output: a pure `lib/pricing/restate-gate.ts` both the component and a Vitest file call, and a
`pricing-tier-form.tsx` whose gate, preview, and dialog copy all read it.

**Deliberate design choice, stated rather than assumed (planning-context constraint):** this repo
has no jsdom/React Testing Library harness, so the decision is extracted into a pure module in
`lib/pricing/` rather than adding a DOM harness. The gate decision AND the dialog copy both move
there, which makes the disclosure itself automatically verifiable — a test can assert the rendered
body names the far-future set, instead of deferring that to a human eye.

**A stale constraint, corrected:** the planning context and `lib/dashboard/data-window.ts` both
state this repo has no vitest alias config. It does — `vitest.config.mts` (committed 11 Sep, added
for plan 06-10) resolves `@/` to the repo root. The new module still imports from `./restate-scope`
by relative path and type-only, so it is unaffected either way; no plan here depends on the alias.

**Scope boundary honoured:** `resolveEditImpact` and `resolveFutureSupersession` are NOT changed,
and `lib/pricing/__tests__/restate-scope.test.ts` is NOT edited — including its deliberate resolver
pin at lines 274-282. Neither file appears in `files_modified`. The resolver half is correct; this
plan does not touch it, and nothing found during planning suggests it should.
