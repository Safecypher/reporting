<planner_notes>
**Column name and shape (07-CONTEXT "Claude's Discretion", 07-RESEARCH Open Question 3, resolved
here):** `revenue_forecast_min_covered_days int not null default 7 check
(revenue_forecast_min_covered_days >= 1)` — the same int-with-check shape `alignment_tolerance`
uses, differing only in the floor (1 rather than 0, because a projection from zero usable days is
not a projection).

**The threshold is measured AFTER the D-02 drop.** `7` means seven *usable* days, i.e. eight
covered days, because the most recent covered day is excluded from the run rate. The field label
and helper text say so, and the forecast RPC (plan 07-04) compares against `usable_days`, not
`covered_days`. Getting this backwards would make the first projection appear a day early.

**Fetcher shape follows `alignment-settings.ts`, not `fy-settings.ts`.** A forecast threshold that
silently defaults to 7 when the real saved value is something else is a money-adjacent surprise —
closer in spirit to WR-03's alignment-settings concern than to the FY start's lower-stakes default
(07-RESEARCH §Security Domain, Known Threat Patterns).

**Do not edit `0023_app_settings.sql` or `0029_app_settings_alignment.sql`.** The convention is
forward-only `create or replace` of `fn_app_settings_audit()` in a new numbered migration; the
`trg_app_settings_audit` trigger itself is left untouched, exactly as 0029 did.
</planner_notes>
