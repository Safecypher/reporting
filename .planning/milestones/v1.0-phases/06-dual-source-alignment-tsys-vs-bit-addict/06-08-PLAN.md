<objective>
Close **WR-04** and **WR-02** in the database, where both belong.

**WR-04:** the level-2 "contributing rows" drill for `enrolled` and `unenrolled` currently returns
the wrong rowset. `enrolled` returns the entire `card_inventory` snapshot for the day — likely
hundreds or thousands of rows when the figure being explained is a handful — and `unenrolled`
returns `removed_cards`, a table Phase 4's own `v_reconciliation_inventory_daily` treats as an
independently-sourced figure it reconciles the inventory drop *against*, not as the same rows.
Neither performs the day-over-day `external_card_reference` set difference the KPI figure
represents. PostgREST cannot express a set difference, so the fix is a new `stable`,
`security invoker` RPC — which is also where this codebase already puts reconciliation logic.

**WR-02:** `tsys_live_cards_baseline_as_of` is stamped on every settings save, so a
tolerance-only edit silently claims the offset was just reconfirmed. Fixing this by
fetch-then-compare in the Server Action would introduce a read-then-write race; a BEFORE UPDATE
trigger makes the rule atomic and takes the column out of the write path entirely.

Purpose: SC4/D-19 promise "drill from either side of any comparison to the contributing rows" —
a user auditing "Enrolled cards: 12" must see those 12 rows. And D-09's whole point is that a
stale offset is *a visible, correctable fact*; an `as of` date that moves without the offset
moving destroys that signal.

Output: two forward-only migrations and two new read-only SQL oracles.

**These migrations are authored here but applied in plan 06-09 Task 1** — a single orchestrator
apply covering 0031, 0032 and 0033 together.
</objective>

    `ci.created_at` and the joined `file_name`, ordered by `ci.external_card_reference` ascending

    1. **Which day's rows are the subject.** `ci.report_date` equals a `case p_direction` that
       yields `p_day` for `'enrolled'` and `(p_day - interval '1 day')::date` for `'unenrolled'`,

       `ci.report_date = null` is never true, an unrecognised `p_direction` returns zero rows.
       That is the whitelist, enforced inside the function — write a comment saying so
       explicitly, because it is load-bearing rather than incidental.
    2. **Which day's rows are the comparison set.** A correlated `not exists` over
       `card_inventory` aliased `o` where `o.report_date` equals the opposite `case p_direction`
       — `(p_day - interval '1 day')::date` for `'enrolled'`, `p_day` for `'unenrolled'` — and
       `o.external_card_reference = ci.external_card_reference`. Use the correlated `not exists`
       form, not a full outer join: 0019's own comment records that a correlated full outer join
       cross-multiplies against every other snapshot day's rows, a real bug caught during that
       implementation.
    3. **The D-07 pairing guard — the trap this task exists to avoid.** Two further `exists`
       clauses requiring that a snapshot exists for `p_day` AND for `(p_day - interval '1 day')::date`.
       Without this, a day whose prior day has no snapshot would return that day's ENTIRE
       inventory (nothing exists yesterday, so every card is "new"), which is precisely the WR-04
       defect re-created through a different route. `v_inventory_daily_diff` has no row at all
       for such a day, so the correct drill answer for it is zero rows.
    4. **The data window.** `ci.report_date >= '2026-08-13'::date`, the same cutoff every view in
       this chain carries.
