# Quick 260908-r3x — Card inventory page

## Problem

Six report types ingest cleanly, but card-inventory and removed-cards data has
no page. Inventory appears only as a diff table inside Reconciliation, so
uploading the report produces no visible result. 912 inventory rows and 4,489
removal rows are effectively invisible.

## Design decisions (made, with reasoning)

**Route `/cards`, nav label "Cards", icon `card`.** The `card` symbol already
exists in `public/icons.svg` — do not invent one; a missing symbol renders as
an empty box with no error.

**Enrolment chart uses a TIME-SCALED x-axis, not a categorical one.** This is
the important call. A categorical axis spaces the 9 snapshots evenly, which
makes 13 Aug → 24 Aug (11 days apart) look identical to 1 Sep → 2 Sep (1 day
apart) — it hides exactly the sparseness the reader needs to see. A time-scaled
axis renders the gaps as whitespace. Use discrete bars or dots at real dates;
do NOT connect them with a line, which would imply we know the values in
between. Caption: "9 snapshots between 13 Aug and 8 Sep 2026 — this report is
not delivered daily."

**Removals chart shows the 4 Sep spike at full linear scale.** 4,426 against a
baseline of tens will flatten every other day to nothing. That is the honest
picture, and the flattening is itself the story. Do NOT use a log axis — this
dashboard's audience includes non-technical leadership, and a log scale makes
a 100× spike look like a modest bump, which is worse than an unreadable
baseline. Instead pair the chart with a short callout naming the incident:
Invex enabled the product to many customers via a mobile-app update on ~4 Sep
and reverted it; the 4,426 removals are that revert, not churn.

**No migration.** Shaping happens in TypeScript over plain table reads. Two
reasons: migration 0022 is authored but unapplied, so anything depending on it
would render a broken page in production; and adding 0023 would create a second
unapplied migration. At 912 inventory rows, fetching `(report_date,
external_card_reference)` and aggregating in TS costs nothing. **Record the
scale assumption in a comment** — revisit with a view if inventory reaches
five figures.

## Tasks

### Task 1 — `lib/dashboard/card-inventory.ts` (+ Vitest specs)

**files:** `lib/dashboard/card-inventory.ts`, `lib/dashboard/card-inventory.test.ts`

**action:**
Pure helpers (no Supabase imports — keeps them unit-testable, matching
`lib/dashboard/bucketing.ts` convention):
- `snapshotSeries(rows)` → `{ day, cardCount }[]` ascending, one entry per
  distinct `report_date`.
- `firstSeenByCard(rows)` → `Map<reference, earliest report_date>`.
- `latestSnapshot(rows)` → `{ day, references[] }` for the max `report_date`.
- `removalSeries(rows)` → `{ day, removedCount }[]` bucketed by
  `removed_at at UTC`.
- `netChange(series)` → change vs the PREVIOUS snapshot, plus the day-gap
  between them, so the UI can say "+1 since 2 Sep (6 days earlier)" rather
  than implying a daily delta.

Server fetchers in the same file, mirroring `verification-drill.ts`'s shape:
read `card_inventory` and `removed_cards` via the session-scoped server client
(RLS applies), filtered to the 2026-08-13 floor.

**verify:** `npx vitest run lib/dashboard/card-inventory.test.ts`
**done:** helpers exported and specced, including the gap-aware `netChange`.
