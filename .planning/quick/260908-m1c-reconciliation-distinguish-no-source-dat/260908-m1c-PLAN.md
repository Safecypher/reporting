<objective>
Make both `/reconciliation` views and tables say **"no source data"** when a source report was never delivered, instead of reporting the absence as a numeric mismatch. Coverage is derived from the ingested rows themselves (min/max timestamp per `source_file_id`), never from file names, because delivery is a rolling window — `daily-ver-report_2026-09-07.csv` actually spans 2026-09-04..2026-09-07.

Purpose: a false mismatch is the most damaging defect this tool can produce. 2,399 transactions across 2026-08-20 and 2026-09-03 are currently presented as billing discrepancies purely because no verification report was ingested for those days — that invites Safecypher to open a billing dispute over transactions nobody was disputing. The core value is *trustworthy* reconciliation; "we don't know" must be visibly different from "the numbers disagree".

Output: migration `0022`, a SQL test encoding the acceptance oracle, and a fourth `no_source_data` state threaded through the status module, the badge, both tables, and the page.

**Design decisions taken here (rationale, so the executor does not re-litigate them):**

1. **`delta` is NULL for a `no_source_data` day.** Delta means "billing minus verifications" — a number-vs-number comparison. When one side has no source data the comparison is undefined, and rendering `+2,387` invites reading absence as a discrepancy of 2,387. NULL makes the "cannot compare" state structurally undeniable and stops any downstream sum from silently folding an absence into a discrepancy total. The raw counts stay visible so the day is still auditable. `short_side` is NULL for the same reason.
2. **Status precedence: `ok` first, then `no_source_data`, then `mismatch`/`needs_review`.** Equal counts is always `ok` — this is what stops quiet days flooding the table with "no report received" when a delivered report legitimately contained zero rows for that day. Only a *disagreement* is gated on coverage. Genuine-mismatch arithmetic is untouched; coverage is a new guard in front of it, not a change to it.
3. **`no_source_data` outranks `needs_review`.** For the newest day, "No report received" is simply more accurate than an amber "pending" and is equally non-alarming.
4. **Inventory is the one exception to precedence 2:** an unbracketed day cannot be `ok`, because `unenrolled_count` is genuinely unknown (there is no snapshot pair to diff), so it is NULL rather than 0 and the day is `no_source_data` outright. Such a day only appears in the view at all when removed-cards rows exist for it, so this cannot flood either.
5. **Coverage is computed for all four sources** (verifications, billing, card-inventory snapshots, removed-cards), not just the two the problem statement names. The same idiom repeated three more times closes the whole false-mismatch class rather than the two instances that happen to be live today. Card-inventory coverage reads the existing `report_date` column — already resolved at ingest time — so no name parsing happens in SQL.

**On task shape:** the tracer-first default is deliberately not applied to Task 1 here. All architectural risk in this change sits in one layer (does the span-based coverage model reproduce the production oracle?), and Task 1 proves that against real production data before a single UI file is opened. Tasks 2 and 3 are then mechanical propagation of one union-type addition.
</objective>
